## 1. 何が「綺麗な光」を作っているのか(v0.25.2633で確定した知見)

M6(洋館の壁灯)が綺麗な理由は **減衰カーブ**。照り返しでも焼き込みでもない
(**照り返しはM6でも既に廃止済み** = v0.25.2149 の負荷対策)。

| 中心からの距離 | 共有 `getGlowTexture` | M6の壁灯 / `getSoftGlowTexture` |
|---|---|---|
| 0%   | 1.00 | 1.00 |
| 25%  | —    | **0.55** |
| 45%  | **0.55** | — |
| 60%  | —    | **0.18** |
| 100% | 0 | 0 |

- **共有カーブは45%でまだ0.55** = 中心付近が広く均一に濃い ⇒ **塊に見える**。
- **M6カーブは早く落ちて尾を引く** = 芯があって外へ消える ⇒ **光に見える**。

### 3つの禁止事項(これを守れば「ベタ塗り」は起きない)
1. **光を `Graphics.fill()` の均一円/楕円で描かない。** `fill` は中心から縁まで同じ濃さで、
   **縁で突然0になる**。加算合成すると必ず「縁のある塊」になる。
2. **薄く広く塗らない。** α0.18のような薄さは、**面積のコストを払いながら光って見えない**
   =一番損。**濃く・狭く**が正解(M6は0.85〜0.9)。
3. **半径に上限を設ける。** 近距離で大玉になると加算オーバードローがベンチのG12 FAIL帯へ入る
   (v0.25.2149の実バグ)。M6は画面高の11%でキャップ。

#### ★提案(未実施・社長裁定待ち): 強glowの半径を縮める
CLAUDE.md のベンチで **G12 は唯一残った FAIL** で、原因は
「再テッセレーションではなく**加算合成の大面積オーバードロー(塗り面積)**」と実測で確定している。
対策として挙がっていたのは **①同時数のキャップ ②半径の縮小 ③解像度削減**で、
③は res1 でも解消せず(v0.25.2648の再計測)、残るのは①②。

**ここで #6 が効いてくる。** ソフトカーブは**外周の寄与が激減する**(45%地点で 0.55→ほぼ0)ので、
**半径を縮めても「光っている面積」の見た目はほとんど変わらない**。
つまり **カーブを直した今なら、見た目を保ったまま塗り面積を落とせる**可能性がある。
- 例: `haloD = radius × 1.7` を **×1.3** にすると塗り面積は **(1.3/1.7)² = 0.58 倍**。
- **ただしこれは「印象を変える調整」なので、カーブ差し替え(#6)とは別の版で出す**
  (§3-1 の掟=変数を1つにする)。**やるなら G12 を再計測して効果を数字で確認する。**

### 3-1f. #9 でやったこと(v0.25.2672)— ★社長指摘「光さ、アイテム形もだと思う」

### ★★訂正: **乗算は使わない**(監査指摘・設計者の誤り)
私は「乗算にすれば影の中でも地面の模様が残る」と説明したが、**これは誤り**。
**黒(RGB=0)の乗算は、黒の通常合成と数学的に完全に同一**:
- 通常: `dst×(1−α)` / 乗算: `dst×(src×α + 1−α)` に `src=0` を入れると `dst×(1−α)` ⇒ **同じ**。
- 「ベタ塗り」の正体は**ブレンドではなく α カーブ**(半径の66%まで α0.94 ≒ ほぼ不透明)だった。

さらに、**乗算にすると影が消える**: `shadowContainer` は `groundLayer` 配下 = **`filteredWorld` の内側**で、
`filteredWorld` は bloom / tilt-shift のフィルタ付き = **透明にクリアされた別RTへ描かれる**。
そこで乗算すると `dst=0` なので**影が丸ごと消滅**する(地面 `groundBase` はフィルタの外・
唯一動いている world 系の乗算 `cloudShadow` は `groundBase` の直上=フィルタの外に置かれている)。

⇒ **影は従来どおり「黒 + 通常合成」。レイヤーも動かさない。**
**乗算とレイヤー移動が要るのは、未決③(影に色を持たせる)を採ったときだけ**——その時は
tilt-shift/DOFとの整合(影だけシャープになる)も一緒に決める。

### テクスチャの焼き方
| テクスチャ | 作り方 |
|---|---|
| 接地の芯 | カーブ `0→1 / 0.52→0.93 / 0.82→0.40 / 1→0` を**起動時に1回**焼く |
| **接地の外側** | カーブ **`0→0.95 / 0.25→0.80 / 0.6→0.42 / 1→0`** を**起動時に1回**焼く |
| **シルエット** | **黒くした絵に縦グラデを掛け、`BlurFilter` を掛けて `RenderTexture` へベイク** |

★**v5訂正: 外側は「既存のソフトカーブを流用」ではない。** v4はそう書いていたが、既存の
`getSoftShadowTexture()` は `0→1 / 0.66→0.94 / 1→0` の**1本だけ**で、これは**「ベタ塗りの正体」として
名指しで否定したカーブそのもの**。**廃止リストに入れておきながら流用と書くのは矛盾**(監査指摘)。
⇒ **上の数値(モックで社長が承認した外側のカーブ)を新規に焼く。**

★**縦グラデ(先端の薄さ)の確定値**(v4は「掛ける」とだけ書いて数値が無く、**シルエットの見え方を
最も左右する所が空欄**だった=監査指摘)。
| 項目 | 値 |
|---|---|
| カーブ(αの実体の下端=0 → 頭側=1) | **`0→1.0 / 0.35→0.92 / 0.7→0.55 / 1→0.15`** |
| 頭側のα | **0.15**(0にしない。0だと**先端が消えて形が読めなくなり**、シルエットの存在理由が失われる) |
| 掛け方 | **αへの乗算** |
| 適用順 | **グラデ → ぼかし**(先にαへ掛けてから `BlurFilter`)。★逆にすると**縁のぼけをグラデが削って硬くなる** |

★**「小さく焼いてから拡大」はやめる**(監査指摘)。Canvas の縮小は高品質リサンプルだが、
**Pixi の RenderTexture へ 1/7 縮小するのはバイリニア1回**で、**細い腕・武器・脚が丸ごと消える**
=「形が分かる」というシルエットの存在理由が失われ、**社長が嫌がったベタ塗りに戻る**。
⇒ **原寸(または1/2)でベイクし、`BlurFilter` でぼかす。** 既存の前例 `farBloomCache`
(`pixiScene.ts` L6222付近・「ベイク時に BlurFilter を掛けて RenderTexture 化」)と同じ作法。
- **ベイクは1回きり**なので per-pixel パスでも**実行時コストはゼロ**(毎フレームのフィルタ禁止は不変)。
- **余白を `blur×3` ぶん確保**してからベイクする(端が clamp されて縁が伸びるのを防ぐ)。
  ★**余白を足したぶん、4隅の計算とUVを補正する**(補正を忘れると**影が余白×2だけ大きくなり、
  足元も上へずれて接地が壊れる**)。
- ★**PMA(3版「明示する」とだけ書いて明示していなかった。ここで確定)**:
  `renderer.render({ container, target: rt })` で焼いた `RenderTexture` は **PMA**。よって
  **黒くする工程で α を壊さないこと**が全て。**手順を1本に固定する**:
  1. 元スプライトを **`tint = 0x000000`** で黒くする。★**黒の tint は RGB を0倍するだけで α に触らない**
     ので、`ColorMatrixFilter(brightness(0))` と**数学的に同じ結果**になり、**フィルタ1パスぶん安い**。
     (★v5訂正: v4は「tint は縁が痩せるので使うな」と書いたが**誤り**。痩せるのは**白**シルエットの話で、
     乗算では明るくできないから既存 `whiteSilhouette` はフィルタを使っている。**黒には当てはまらない。**)
  2. `BlurFilter` を掛けて `resolution: 1` の `RenderTexture` へ焼く。
  3. 出来たテクスチャは **PMAのまま `Sprite`/`PerspectiveMesh` に貼り、`tint` は掛けない**。
     濃さは**スプライト側の `alpha` だけ**で調整する。`blendMode` は既定(`normal`)。
  - 確認: **焼いたテクスチャの縁が元の絵の縁より痩せていないこと**。
    ★**痩せていた時に疑う先は 3つ: ①余白が `blur×3` 足りない ②`resolution` が 1 でない
    ③焼いた後にPMAを解除している。** tint は原因ではない。

### ★密集時の黒潰れについて(正直に書く)
通常合成の黒は重ねるほど `1−Π(1−α)` で濃くなるので、**体をまたぐ重なりは1体内の上限では止まらない**
(10体重なれば理屈上ほぼ真っ黒)。**完全に解くには全影を1枚のRTへ集めて max 合成する=1パス増**で、
これはこのプロジェクトで一番避けたいコスト。
⇒ **方針**: **いまは作らない。** 現行実装も同じ性質を持っており、社長からの指摘も出ていない。
**新実装は面積が増えるぶん悪化しうる**ので、**受け入れ条件の「密集10体」で実機確認し、
潰れて見えたらその時に初めてRT合成を検討する**(未実施の選択肢として記録)。
**数値で保証する条件は書かない**(書いても満たせない条件になるため)。

### 台形(足元へ絞る)
**`PerspectiveMesh`(Pixi 8.19)** を使う。近い辺=`足元 ± 絵幅×絞り/2`、遠い辺=`足元+向き×長さ ± 絵幅/2`。
- ★**分割数 `verticesX = 8` / `verticesY = 12`**(v6まで空欄=監査指摘)。台形の遠近補正は頂点単位なので、
  **粗いと台形の中でシルエットが波打ち、細かいと頂点更新が増える**。縦を多めにするのは
  **伸びる方向が縦(足元→頭)**だから。★**この値は事前計測(SHD-M)で使っている値と同じ**にすること
  (別の値で測ると計測の意味が無くなる)。
- ★**左右反転は「4隅の左右を入れ替える」で行う**(v6まで「UVで」としか書いていなかった=監査指摘)。
  `setCorners()` は透視補正のため**uvを内部で作り直す**ので、外からuvバッファを書き換えても戻される。
  **4隅の入れ替えなら焼き直し不要**=キャッシュ半減の前提はそのまま成り立つ。
- ★**退化ガード**: 長さ ≤ 2px、または幅 ≤ 2px なら**描かない**(浮遊フェード時・光方向が縮む時)。
- ★**`roundPixels` の外**なので**位置は自分で整数丸めする**(本体は止まっているのに影だけ半px揺れるのを防ぐ)。
- ★**メッシュはスプライトのバッチに入らない**ので、「プール済みスプライトは事実上ただ」の実測は
  **そのまま適用できない**。**枚数上限と実測が要る**(下記「計測」)。

### ポーズ追従(★未定義だと社長が直したかった違和感が残る)
**左右反転・歩行コマ・被弾しなり(skew)・`depthScale` に追従する。**
反転は**UVで対応**(焼き直さない)。
★**skew は"変換"ではなく"4隅の計算"に織り込む**——`PerspectiveMesh` にローカル skew を掛けると
**近い辺(足元)まで動いて接地が横滑りする**。**先端側の隅だけを skew ぶんずらす。**
★**ずらす向きは「光方向に直交する軸」**(=倒した先での横方向)。**光方向へずらしてはいけない**——
光方向へずらすと**しなりが「影の伸び縮み」に化ける**(被弾のたびに影の長さが変わる)。

### 光の向きと上下の副作用(★CLAUDE.mdの5点チェック)
昼の `SUNLIGHT_SHADOW_DIRECTION = (0.7, −0.28)` = **影は画面奥(上)へ伸びる**。
- ★**`PerspectiveMesh` は頂点カラーを持たない**ので「先端だけ薄く」は**メッシュ側では作れない**。
  ⇒ **2段で解く**:
  1. **先端の薄さは"焼く"**。シルエットをベイクする時に**縦方向のグラデを掛ける**
     (足元=不透明 → 頭側=薄い)。**ベイクは1回きりなので無料**。楕円が持っていた「先へ行くほど薄い」も同時に戻る。
  2. **地平線帯は"長さで"解く**。**先端が帯を越えないよう長さを詰める**(足元Yと帯の位置から上限長を計算)。
     αを触らないので**足元の接地が薄くならない**(メッシュ全体のαを落とすと接地まで消える)。
- ★**可視域の判定も先端で行う**(最大引き `?zoomlock=1` を含む)。★**判定した結果どうするか(3版未定義だった)**:
  **カリング(描く/描かない)にだけ使う。** ★**判定は「足元→先端の線分と可視矩形の交差」**で行う。
  ★**「両端が外なら描かない」ではいけない**(v4の誤り): cineのボス(615px)のように
  **両端が画面外で中間だけ画面を横切る**配置があり、**影が丸ごと消える**(監査指摘)。
  ★**可視域を理由に長さを詰めてはいけない**——詰めると**引きズームで影だけ縮む**という別の破綻になる
  (`CONTEXT_ZOOM_MIN` で可視域が変わるため、ズームのたびに影の長さが動く)。
  長さを詰めてよいのは**地平線帯**の理由のときだけ。

### ★接地2枚は「回さない」(v6から未回答だった=監査指摘。v7で確定)

**新しい接地2枚は回さない。画面軸のまま平らに置く。**
理由: ①接地の芯は**「地面に立っている根拠」**であって方向を持つ絵ではない
②**夜の既定 `(0.42,1)` はほぼ縦向き**なので、回すと**縦に立った細長い楕円**が足元に置かれ、
接地パッチに見えなくなる ③**v7では光が毎フレーム振れる**ので、回すと
**爆発のたびに足元の楕円がくるくる回る**。

**閾値そのものは実測後に決める**(★未決E)。

### 浮いている時
高さ h に応じて **小さく(1−0.35·t) / 薄く(1−0.5·t)**。
★**`t` の正規化(v6まで空欄=監査指摘)**: `t = min(1, h / (絵の高さ × 1.2))`。
**絵の高さを基準にする**ので、跳躍(数十px)と登場演出(数百px)で同じ式が成り立ち、
**大きいキャラほど同じ見た目の高さで同じ効果**になる。
★**ぼかしは変えない**(設計判断)。ぼかしは**ベイク時に焼き込む**方式なので実行時に強められず、
高さ別に2枚焼くと**キャッシュが倍**になる。**大きさとαだけで浮遊は十分伝わる**ので、そこは割り切る。
(実行時に `BlurFilter` を足すのは**禁忌**。per-pixel パスなので絶対にやらない。)
★**投影点は「地面」= 描画上の足元Y **＋** 高さ**(画面Yは下が正。**描画の足元は既に高さぶん持ち上がっている**ので
足す。引くと**影がキャラより上へ逃げる**)。**「足元Y」は描画基準(持ち上げ後)**と定義する。
高さは描画側が持つ値(登場演出・跳躍)を使う。★**いまは登場演出中に影を出していないので着地で
無から現れる**。これも直す。

### ★★影は「1体につき1枚」。向きと長さは"支配光"が決める(v7の中核・社長裁定)
> 社長「今回の影は**爆発等で伸びることが前提**での承認」

**環境影と投影影を別々の仕組みにしない。1体のシルエットは常に1枚だけで、
その向き・長さ・濃さを"その場の光"から毎フレーム計算する。**

**支配光ベクトル `Ldom` の作り方**(1体につき1回):
```
Ldom = w_amb × dirAmb + Σ_glow ( w_g × dirAwayFromGlow )
w_amb = 1（ステージ照明。常時）
w_g   = falloff × strength × life × GLOW_SHADOW_WEIGHT
        falloff = 1 − dist/reach（既存の投影影と同じ）
```
- **向き** = `normalize(Ldom)`
- **長さ** = `絵の高さ × 比率 × (1 + GLOW_STRETCH × min(Σw_g, GLOW_SUM_CAP))`
  ⇒ ★**爆発が近いほど影が伸びる**。★**`Σw_g` は必ず頭打ちにする**——上限が無いと
  強glowが重なった時に青天井になり(glow5個で Σ≈8)、**96pxの敵に600px・500pxのボスに3000px超**
  の影が出る(監査指摘)。**`GLOW_SUM_CAP = 2.0`**(=長さ最大2.8倍・濃さ最大2.2倍)。
- **濃さ** = `基準濃さ × (1 + GLOW_DARKEN × min(Σw_g, GLOW_SUM_CAP))`
  ★**頭打ちは「合成後のα」ではなく「倍率」に掛ける**(合成αを頭打ちにすると、どの層を削るかという答えの無い問題になる=上で廃止した上限と同じ罠)。
- ★**強い光が複数あっても、影は1本のまま**(ベクトル合成なので放射状に増えない)。

**この方式が同時に解決すること**:
1. ★**「爆発で影が伸びる」**——社長の承認の前提そのもの。線3本の疑似投影影ではなく、
   **本物のシルエットが伸びて振れる**。
2. **1体から向きの違う影が2本出ない**(合成なので常に1本)。⇒ 旧★未決Cは**消滅**。
3. **足元のベタ塗り楕円が要らない**(接地の芯が常にあるので、投影影用の楕円は不要)。
   ⇒ 旧★未決Bは**消滅**。
4. ★**ヒステリシスが要らない**(光源を"選ぶ"のをやめて"足す"ので、勝者交代のちらつきが原理的に無い)。

**★★負荷について(v7訂正・監査指摘で前言を撤回)**:
私は当初「今いちばん高い物を置き換えるので**安くなる見込み**」と書いたが、**この比較は成立しない**。
| | 旧(投影影) | 新(シルエット) |
|---|---|---|
| **いつ払うか** | ★**強glowが生きている間だけ**(数百msの一過性) | ★**強glowが1個も無い平常時も、全フレーム** |
| ドローコール | **1つの `Graphics` にまとめ描き=実質1〜2** | ★**1体1メッシュ×固有テクスチャ=40〜90＋バインド** |
| 頂点更新 | ジオメトリ再構築(CPU) | 毎フレーム4隅。★**爆発中は静止物(木/壁/建物)まで全部動く** |
⇒ **ピークが下がっても、プレイ時間の大半を占める平常時に、これまで無かった常時コストが載る。**
⇒ ★**「プール済みスプライトは事実上ただ」の実測は持ち込めない**——あれは
**全部が同じ焼きテクスチャ=1バッチ**の条件で取った値で、**メッシュはバッチに入らない**。
⇒ ★**安いか高いかは、実装前に測って決める**(下記「事前計測」)。**設計の前提が崩れたら方式を変える**
(台形をやめてスプライトの回転で近似する等)。

★**あわせて訂正**: 「強glow 1個につき世界中を走査」は**現在は誤り**。v0.25.2703(影#1)で
**候補の走査は1フレーム1回へ巻き上げ済み**(`pixiScene.ts` の `buildCasterCandidates`)。

**「常に光っているからそう見えていただけ」で、伸び縮みの動きは測れていなかった。**

**★ただし、測り漏らした方向は"安い側"**(だから結論は変わらない):
- **上限に張り付く=常に最大の長さ=塗る面積が最大** ⇒ **測ったのはフィル面の最悪ケース**。
  伸び縮みすれば短い時間ができるので**平均はむしろ安くなる**。
- **4隅の書き換えは、動く量に関係なく毎フレーム同じ回数**(`setCorners` は位置を書くだけ)。
  「大きく動く」から高くなる、という性質ではない。
- 実際の塗り面積: 台形 ≈ 長さ336 ×(足元16+先端78)≈ **31.6k px/枚 × 90 = 約2.84M px/フレーム**
  = **画面約2.8枚ぶんの影の重ね塗り**。それで60fps。

#### ★結論(着手可否)
**着手前に決めていた分かれ目「Δadj 1.0ms未満 ⇒ そのまま進む」を、2端末とも満たした。**
- メッシュ90枚 / 1枚ずつ別テクスチャ / 最大まで伸びた状態 / 強glow24個 / 支配光の実計算あり
  ⇒ **すべて同時で 60fps(旧投影影オフ)**。
- ★**旧実装は同じ glow12 で avg 41.5〜42.6** だったので、**方式の置き換えは純粋な改善**。
⇒ **§3-9-B v8 の方式(1体1メッシュ・支配光・台形)で実装に進んでよい。**
★**残る唯一の注意**: 全段が vsync 天井(60.0)なので、分かったのは**「割らない」まで**。
**1枚あたりの実コストは未知**のまま(=余裕がどれだけあるかは分からない)。

★**`Ldom` に参加する光の定義(v6まで未定義=監査指摘)**:
**参加するのは強glowだけ**(今の投影影と同じ集合 = `effects[]` の `kind==='glow'` かつ
`radius >= STRONG_GLOW_RADIUS`)。
- ★**松明・焚き火・城/商人のグロー・緑卵の光・プレイヤーライトは参加しない。**
  これらは**スプライトであって effect ではない**ので今の投影影も拾っていないし、
  **参加させると常設の光で画面中の影が常時ねじれて落ち着かなくなる**(松明が並ぶ廊下で全部の影が泳ぐ)。
- ⇒ **受け入れ条件の「松明が何本も並ぶ場面」は"影が動かないこと"を確認する項目**(逆向きの確認)。

**残すもの**:
- ★**光源直下の暗いディスク(`shadeAlpha` の楕円)は残す**(消すと無断の演出削除になる)。
- ★**シルエット対象外のルール(松明/焚き火/緑卵)は支配光の計算にも同じく適用**。
  松明は投影影の主要キャスター(weight 0.82)なので、書き忘れると**そこだけ炎の黒い塊が伸びる**。

**★未決E(実装後に実測して決める)**: `GLOW_SHADOW_WEIGHT` / `GLOW_STRETCH` / `GLOW_DARKEN` /

### 実装者への指定(監査3回目で足りていなかったもの)
- **`RenderTexture` の resolution は 1 に固定**(既存 `whiteSilhouette`/`grayscaleTexture` と同じ書き方だと
  端末解像度で**バイト数が最大4倍**になり、32MBの見積りが崩れる)。
- **焼き込む縦グラデの原点は「αの実体の下端」**(余白を足した後のテクスチャ下端ではない)。
  間違えると**足元が薄い影**になり、目的の逆になる。
- **skew の織り込み量** = `tan(skew) × 絵の高さ`。★**ずらす向きは「光方向に直交する軸」**、ずらすのは
  **先端側の2隅だけ**。★**光方向へずらしてはいけない**(しなりが影の伸び縮みに化ける)。
- ★**「高さ」と「フェード」の取り方**(★このプロジェクトが繰り返している「1経路だけ配線して
  残りがポップ」を**構造で潰す**。ただし v5 で**2つを別扱いに分けた**——監査指摘のとおり、
  フェードは差分から導出できない)。

  **(a) 高さ = 描画結果の差分から取る(導出でよい)**
  - **高さ** = `(論理の足元Y) − (実際に描かれたスプライトの足元Y)`。描画側が既に持ち上げているので
    **持ち上げ量そのものが高さ**。**登場演出 / 跳躍(かぼちゃ・ハンター・巨人) / 盾で弾かれた落下
    (`SHIELD_BLOCK_FALL_MS`) / 救援アライの飛来・離脱**が**個別配線なしで全部乗る**。
  - ★**座標系を揃える**: **両方とも `shadowContainer` と同じ空間(world/親ローカル)で取る**。
    画面座標で取ると**カメラのズーム/シェイクが高さに化ける**。
  - ★**不感帯 6px**: 描画側には持ち上げ以外の微小なYずれ(`footY − 2` 系の調整・テクセル丸め・
    ボスの描画オフセット)があるので、**差分6px以下は高さ0**とし、超えた分から6pxを引いて使う
    (段差を作らないため)。★**これが無いと、地上に居るのに全アクターが常時「少し浮いている」
    と誤判定され、影が下へずれて小さく薄くなる**(1本化した仕組みなので誤爆は全員に出る)。
  - ★**アイドルの上下動が高さとして読まれるのは正しい挙動**(絵が浮いた分だけ影は地面に残る)。
    ★**ただし数px規模のアイドルは不感帯6pxに飲まれて消える**(監査指摘の衝突)。
    **ここは不感帯を優先する**——数pxの上下で影が動くより、地上のアクター全員が
    常時ずれない方が大事。**十数px以上動くアイドル/跳躍は不感帯を越えるので拾える。**
  - ★**「論理の足元Y」が地面を表していないアクターは、この方式では高さが出ない**(監査指摘)。
    **ストア座標そのものが空中を動くもの=救援アライの飛来・離脱**がこれに当たり、
    差分が0なので**影が本体に張り付いて空を飛ぶ**。
    ⇒ **救援アライだけは飛行高度を明示的に渡す**(この1件は経路が特定できているので配線する)。
    **受け入れ条件に「救援アライの飛来中、影が地面に残っている」を入れる。**

  **(b) フェード = 描画側が「退場系だけを掛けた値」を1つ持つ(導出しない)**
  - ★**`view.container.alpha × view.sprite.alpha` をそのまま使ってはいけない**(v4の誤り)。理由2つ:
    1. **地平線フェードが二重に掛かる**。既存の `syncShadows` は `horizonActorAlpha(footY)` を
       影のαとして**別途渡している**のに、本体のコンテナαにも同じものが入っている
       ⇒ そのまま掛けると**地平線際で影だけ二乗で消える**。
    2. **「消えかけている」ではないαまで拾う**。**裏ボスの裏回り透け(`BOSS_BEHIND_ALPHA`)**は
       *存在の消滅ではない*のに影まで薄くなり、**プレイヤーが回り込むたびにボスの影が消える**
       (`BOSS_BEHIND_ALPHA=0.5` は CLAUDE.md に「意図的な floor」と明記されている値)。
       同じく**ゴーストの常時α(`GHOST_ALLY_ALPHA`)**・**無敵点滅**も影に掛けてはいけない。
  - ⇒ **各描画関数(`drawPlayer` / `drawEnemy` / ボス / NPC / escort)が、本体αを組み立てる時に
    「退場・死亡由来の係数だけ」を掛けた `view.shadowFade` を1つ持つ。** 影はそれだけを読む。
    ★**掛ける**: `playerDeathAt`→`deathFade` / 敵の `artFade` / `hunterLeavingAt`+`HUNTER_LEAVE_FADE_MS` /
    `savedAt`+`RESCUE_OUTRO_MS` / 裏ボスの討伐フェード。
    ★**掛けない**: 地平線フェード(影側が既に持っている) / 裏回り透け / `GHOST_ALLY_ALPHA` /
    無敵点滅 / `corridorRunInFade` 等の演出用の一時透過。
  - ★**配線先は「跳躍の経路(多数)」ではなく「描画関数(5つ)」**なので、数え切れる。
    実装後、上の「掛ける」5場面で**影が本体と一緒に消えること**、「掛けない」4場面で
    **影が消えないこと**を目視で確認する。
- **影リクエスト構造体(`{x,y,w,alpha}`)を拡張**する(シルエットには**テクスチャ・表示実寸の高さ・
  反転・`shadowFade`**が要る)。★**対象は商人/イベントNPCだけではない**(v6の書き漏れ=監査指摘):
  **城 / 病院 / 武器庫 / 警察署 / 拾い物 / 設置武器(shield・decoy・turret) / 花 / 木 / 壁 /
  プロップ / city props** も全部シルエット対象になったので、**同じ拡張が要る経路を全部洗う**。
  ★**洗い方は「この技」ではなく「この動作(=影を落とす)」で洗う**(CLAUDE.md の教訓)。
- **裏ボスの「絵の下端」**は判定(`e.y+e.height`)ではなく**スプライトの実体下端**から取る。
- **影プールの構造変更**: 現状 `shadowPool: Map<string, Sprite>` は**1体1枚**前提の mark-and-sweep。
  **1体3個・スプライトとメッシュ混在**になるので、鍵の付け方・破棄・`?shadow=0` の全破棄経路を作り直す。
- **死亡/退場時のフェード**: 現状は `seen` から外れて即 `destroy`(ポップ)。**面積が増えるぶん目立つ**ので、
  本体のフェードに合わせて影も薄くしてから消す(取得元は**上の `view.shadowFade` 1本**。
  ★**`container.alpha × sprite.alpha` は使わない**——地平線の二重掛けと裏回り透けの誤認が入る)。
- **オンデマンド・ベイクの予算**も **4枚/フレーム**(事前ベイクと同じ)。
  ★**4の根拠(v6まで無かった=監査指摘)**: 1枚 = 「RenderTexture確保 + BlurFilter 1パス」で、
  **128²級なら1枚あたり1ms未満と見込む**が**実測していない**。
  ⇒ ★**実装したら最初に、事前ベイク中のフレーム時間をログで1回見る**。
  **16.67msを割るなら4を下げる**(2 → 1)。受け入れ条件に**「出撃直後にコマ落ちしない」**を入れる。
  ★v7で**静止物の種類(約40)が出撃直後に加わった**ので、開始直後の負荷はv6より増えている。
- **地平線帯の詰めには不感帯と平滑化を入れる**(昼のみ効くが、**ボスが上下に歩くたびに影が伸縮する**)。
  ★**数値(v6まで空欄=監査指摘)**: **不感帯 12px**(帯の手前12pxまでは詰めない)、
  **平滑化は時定数 180ms の指数平滑**(長さに掛ける)。
  ★**「伸びる」と「帯を越えない」の優先順位**: **帯が勝つ**(空へ影が出る方が事故として大きい)。
  ただし**詰めるのは長さだけ**で、αは触らない(足元の接地を薄くしない)。
- **`?silshadow=0` は今回足した新規挙動を全部戻す**: シルエット / 接地2枚化 / 長さの新規則(絵の高さ×比率)/
  個体倍率の廃止 / `flatSize`・`BOSS_SHADOW_TINT`・`FLOWER_SHADOW_*` の廃止 / 地平線帯の詰め /
  浮遊時の投影点と縮小 / 退場フェード / 外側オフセットの上限。
  ★**さらに v7 で足す分**: 支配光の合成(爆発で伸びる)/ 旧投影影の廃止 / 静止物のシルエット /
  `OBJECT_SHADOW_MAX` の枚数キャップ廃止。
  ★**「環境影の下限0.35」と「光源選択のヒステリシス」は v7 では不要になった**——
  光源を"選ぶ"のをやめて"足す"ので、**両方0になる帯も勝者交代のちらつきも原理的に起きない**。
  **実装者はこの2つを作らない。**
- ★**見え方に関わる数値は全部この節に確定値がある**(v7時点。未決D=濃さの基準だけ社長裁定待ちで、
  初期値 D-1 を置いて着手してよい)。
  **確定値が無い項目に出会ったら、実装者は自分で決めずに ★未決へ書いて止まる**
  (CLAUDE.md「実装精度の規律」1)。
- **静止物(木/壁/プロップ)も接地の外側の位置が変わる**(長さの規則が変わるため)。
  ★**受け入れ条件の確認場面に「木/壁/プロップの見え方が破綻していないか」を足す。**
- **密集の黒潰れの"安い緩和策"を先に用意しておく**(実機で潰れた時、いきなりRT合成の作り直しにしないため):
  ①シルエットαだけ下げる ②重なり数で減衰 ③接地の外側を薄くする。**この順で試す。**

### 計測(★段取りを直した)
1. **実装後に** `?silshadow=0` / `=1` の**両方**で `?benchonly=FXG` と `?benchonly=ALL` を1本ずつ。
   (着手前は `=1` が存在しないので測れない。)
2. **`ALL` は新計測器で未計測の系統**なので、**まず `=0` で基準を取る**。
3. 読むのは **`Δadj` → `shift` → `n`**。**`shift` を見ずに離れた段を比べない。**
4. ★**メッシュはバッチに入らない**ので、**ドローコール数**も見る。
   ★**v7の最悪ケース(全部入りで数え直した)**: シルエットは**アクター＋静止物**に付き、
   **1体1枚**(光が何個あっても増えない)。⇒ **同時に可視な"影を落とす物"の数**が上限。
   **密集10体＋プレイヤー＋護衛/NPC＋巨大ボス＋木/壁/プロップ/city props/建物**で
   **おおむね40〜90メッシュ**。**最大引き(`?zoomlock=1`)は可視域が広がるので最悪ケースはここ。**
   ⇒ **測る場面 = `?zoomlock=1` の密集＋巨大ボス＋強glow多数(爆発中)**。
   ★**4隅は毎フレーム動く**(歩行コマ・skew・`depthScale`・浮遊・**支配光の振れ**)ので、
   静止した敵で測らないこと。
5. ★**いちばん重要なA/Bは「強glowが出ている場面」**。旧実装はそこで
   **強glow 1個につき約88図形 × glow数**を per-frame `Graphics` で描いており、
   **実測で強glow 1個 ≈ 2ms**。新実装は**光源数に依存しない**ので、
   **`?benchonly=FXG` の強glow段(FXG G8/G12)で `=0` と `=1` を比べるのが本命**。
   ★**ここが改善していないなら、方式の前提(光源数に依存しない)が実装で崩れている**ので、
   数値を触る前に実装を疑う。
6. 負荷の受け入れ: **Δadj の増分が 1.0ms 未満**なら採用。超えたら遠いものから接地2枚へ縮退。
   ★**閾値を測れる条件で測る**: 基準段は vsync 天井で Δadj が一律過小に出るので、
   **天井を割っている段(密集/巨大ボス/ALL)で比べる**。`shift`(熱ダレ)が数msあるので、
   **同一runの中の `=0` と `=1` を比べる**(別runの絶対値を比べない)。

### ★★未決A → **解決済み(社長裁定 2026-08-02・数字を見た上で「まずAで実装して実機で見る」)**
**絶対pxの上限(160px)を置くと、廃止したはずの「大物ほど影が相対的に小さい」を再導入してしまう**

## ★3-9-C. 影の作り替え(v12)— 「1本の影を動かす」をやめる + 内側フェザーの半影

**社長承認済み。S-5〜S-8 を置き換える。v11 から品質監査2回目の指摘と社長裁定を反映した版。**

### ★根本原因(2つ・どちらも「動かす」前提から出ている)
**原因1: 1本の影を2つの向きの間で動かしている。** 1本の影が向きAから向きBへ移る限り、
**先端の経路が直線でも角度は必ず掃く=回る**。社長の実機報告が証明した ——
「`?glowfade=0` だと**確かに回らない**けど即座に戻ってコレジャナイ」。
**移動時間をゼロにすると回転が消える**=回転は「移動」から出ている。

**原因2: 光の"明るさ"が影の"長さ"を動かしている。**
```ts
pixiScene.ts:8853   const strength = (1 - dist / L.reach) * L.life * SHADOW_GLOW_WEIGHT;
//                                    ↑ 位置(falloff)        ↑ 明るさ(life)  → 長さにも濃さにも効く
```
**光が暗くなっても影は縮まない。** 長さ・向きは光の**位置**だけ、明るさは**濃さ**だけに効く。

### ★新しい原則: **光1つ = シルエット1枚**
| 場面 | 挙動 |
|---|---|
| 爆発が点く | 爆発のシルエットが**フル長で即座に**出る(長さ・向きは光の**位置**で決まる) |
| 爆発が減衰する | ★**長さも向きもそのまま。α だけ薄くなる** |
| 爆発が消える | α が 0 になっている。★**切り替える瞬間が存在しない** |
| ★**物体が動いた** | ★**影も動く**(向き=物体足元−光源。**自然の法則に従う**=社長裁定) |

## ★A. 半影(ペナンブラ)— **④内側フェザー**(社長裁定 v0.25.2773「では4」)

> **実装済み: v0.25.2817**(★D-2 と同じコミット)。`pixiScene.ts` の `bakeSilhouette` を
> **3パス**(a_hard / a_soft / 合成Filter)に書き換えた。ツマミ `?penumbra=0`(=旧1パスに戻す)/
> `?penumbrahard= ?penumbrasoft= ?penumbrak0= ?penumbrak1= ?penumbrapow=`。**pad は1pxも増えていない**
> (`SHADOW_BLUR_PAD_MULT=3` のまま)=常駐メモリ増ゼロ。中間の2枚は焼き終わり次第 destroy。
> k(t) の式は `src/utils/shadowBake.ts` の `penumbraWidth` に同じ形で置き、端点・単調増加・
> 「先端でも k<1(本影が残る)」をユニットテストで固定した。**実機確認は未実施(社長)**。

### ★言葉の訂正(これが設計を1回間違えさせた)
社長の「**縁を崩す**」を設計チャットが**ランダムノイズで虫食いにする**と読んだのは**誤り**。正しくは:
> **遠端ほど半影の幅を広げ、輪郭のコントラストを滑らかに落とす**

半影は**面光源の幾何**から出る(遮蔽物→受光面の距離が増えるほど広がる。NVIDIA PCSS と同じ考え方)。
**虫食いは荒れた地面・煙・木漏れ日が無ければ実際の影には出ない。** 物理の順位は **② > ③ > ①**。
★**ノイズ案(①)は不採用。ディザも不採用**——影は台形へ**最大2.8倍まで非一様に引き伸ばされる**ので、
**ノイズ粒もディザ格子も縦だけ伸びて破綻する**(モアレ)。

### ★方式: 外へにじませず、**輪郭の内側**でαを落とす
```
a_hard = blur(SHADOW_BLUR_FRAC × 0.25) のα      ← 外形はこれで決め打ち(=外へ広がらない)
a_soft = blur(SHADOW_BLUR_FRAC × 3.0)  のα      ← 「縁からの距離」の代用として使うだけ
k(t)   = 0.06 + (0.86 - 0.06) × t^1.15          ← t=0 足元 / t=1 先端。半影の幅
a_out  = a_hard × smoothstep(0, k(t), a_soft)
```
- ★**余白(`pad = blurPx × SHADOW_BLUR_PAD_MULT`)を1pxも増やさない ⇒ メモリ増ゼロ。**
  (②を素直にやると `pad` が3倍になり、512pxベイクで **1.32MB → 1.94MB = +47%**。
   この数字は資料値ではなく **`SHADOW_BAKE_MAX_LONG_EDGE=512` / `SHADOW_BLUR_FRAC=0.02` /
   `SHADOW_BLUR_PAD_MULT=3` から計算したもの**。④ではこのコストが丸ごと消える。)
- ★**引き伸ばしに強い**: 側面の縁のフェザー幅は**横方向**で測られるので、台形が縦に2.8倍伸びても
  **設計どおりの幅を保つ**。伸びるのは先端の端だけで、そこは遮蔽物から最も遠い=半影が広くてよい場所。
- ★**濃さの縦カーブ(既存 `[[0,1.0],[0.35,0.92],[0.7,0.55],[1,0.15]]`)は最後に掛ける**(不変)。

### ★実装手段は**カスタムFilter(GPU)一本**。`extract` によるCPU読み戻しは使わない
- 上式は**画素ごとの演算**なので、`renderer.extract` で読み戻して Canvas2D で処理する手もあるが、
  ★**GPU→CPU読み戻しは同期待ちでフレームを止める**。ベイクは**ゲーム中に新しいスプライトが出るたび**
  走るので、そこで hitch が出る。⇒ **2枚(hard/soft)を RenderTexture へ焼き、
  第2サンプラを uniform に渡すカスタム Filter で合成する。**
- ★**ベイク時間は現行と同程度**に収まる想定なので **`SHADOW_BAKE_BUDGET_PER_FRAME = 4` を据え置く**
  (v11案の「3タップ合成でベイク3倍 ⇒ 予算 4→2」は**算数も間違っていた**: 4×1=4 に対し 2×3=6)。
  ★**既存の `silhouetteBakeTimeLoggedOnce`(`pixiScene.ts:8707`)で1枚あたりの実測msを必ずログに出し、
  4枚合計が16.67msを割るなら予算を下げる**(判断材料を残す)。
- ★**3タップの重ね塗り(v11案)は採らない**。`clear:false` の source-over は
  `a_out = a₁ + a₂(1-a₁)` で**加算にならない**ため、タップ境界に**明るい帯が2本入る**(監査指摘)。
  上式は1パスの画素演算なので**帯が構造的に出ない**。
  ※もし将来2枚合成に戻すなら、**加算ブレンド + 相補マスク**(`a₁m + a₂(1-m)`)にすること。

### ★受け入れ条件(半影)
- **足元の縁が現在より硬く、先端の縁が滑らかに広い**こと。
- ★**余白(`pad`)が現行から1pxも増えていない**ことをコードで示せること(=メモリ増ゼロ)。
- ★**先端中央の本影が消えていない**こと(αが0にならない)。濃さのカーブが先端で既に0.15まで
  落ちているので、フェザーを掛けすぎると**夜の地面で影が消えたように見える**。
- **2.8倍に伸ばしても側面の縁の幅が変わらない**こと。

## ★B. 層の構成
★**接地2層(outer/core)は「光」ではなく「足の接地」を描いている**ので、光ごとに増やさない。
| 層 | 何枚 | 爆発の影響 |
|---|---|---|
| **接地アウター + 接地コア** | ★**常に1組だけ** | 濃さは**受けない** |
| **シルエット(メッシュ)** | **光1つにつき1枚** | 環境光1枚 + 爆発 最大2枚 |

**なぜ**: v10案の「爆発影も3層」だと `SHADOW_CORE_ALPHA_BASE ≒ 0.589` の楕円が**同じ足元座標に最大3枚
重なり**、実効α 0.589→**0.93**。承認済みの足元が別物になり、しかもその上乗せが `falloff×life` で**明滅する**。

★**接地アウターの寄せ方向(監査2-2への回答)**: 現行 `pixiScene.ts:9039/9056` は `ldom.dirX/dirY`(支配光)で
アウター楕円を寄せている。支配光は廃止するが、**アウターは寄せ続ける**(v9の足元の見え方を変えないため)。
⇒ ★**「環境光 + 描画中の爆発光」のうち `falloff × life` が最大のもの1つの向き**を使う
(接地層専用に1本だけ選ぶ。シルエット側の複数光とは無関係)。**濃さは変えない。**

## ★C. 濃さの決め方
★**監査が見つけた事実**: `SHADOW_GLOW_DARKEN`(1623) と `darkMult`(8832/8899) は
**計算されて返されているが `placeShadowV9` が一度も読んでいない完全な死にコード**
(`ldom.` の読み出しは 9039/9056/9077/9088/9089/9092/9115/9118 のみ)。
⇒ ★**v9 に「爆発で影が濃くなる」挙動は存在しない。** v9 は勝者総取りなので
**爆発中に見えている影は `SHADOW_SIL_ALPHA_BASE = 0.46` の1枚**だった。

```
Σ  = Σ(falloff × life)  ただし ★実際に描いている爆発シルエットのぶんだけ。0..1 でクランプ
爆発シルエットα = SHADOW_SIL_ALPHA_BASE × falloff × life
環境光シルエットα = SHADOW_SIL_ALPHA_BASE × max(0, 1 − Σ × SHADOW_AMB_WASH)   ★WASH = 2.0
```
- ★**Σ の範囲を「描いている光」に限定する**(監査 致命2 への回答)。v11案は範囲が未定義で、
  素直に「圏内の全光」と読むと**混戦(強glow6個)で Σ=1.8 → 環境光0、各爆発影も薄く、影がほぼ消える**。
  さらに48枚キャップで切られたキャスターは**環境光だけ洗われて爆発影も出ない=影ゼロ**だった。
  ⇒ **描画とΣを必ず一致させる**ことで、この穴が構造的に閉じる(キャップで切られたら Σ=0=環境光フル)。
- ★**`SHADOW_AMB_WASH = 2.0`**(監査 C-5 への回答): Σ=0.5 で環境光が消える。
  v9 の勝者交代点(`falloff×life > 1/2.2 ≒ 0.4545`)とほぼ一致するので、
  **中距離でも実質1枚になり v9 の絵に寄る**。v11案(WASH=1.0)は中距離で「半分の濃さの影2本」になり、
  社長が以前指摘した「ベタ塗りが重なってる感」を再発させるところだった。
- ★**接地2層は薄めない**ので、閃光の間も足元の接地は消えない。

## ★D. 仕様

**S-12-1. スロットとプール鍵**
- プール鍵は ★**`${req.id}#amb` / `${req.id}#x0` / `${req.id}#x1`** の**固定3枚**。
  ★**光IDを鍵にしない**(爆発のたびに `PerspectiveMesh` + geometry を新規生成し、
  `SHADOW_MESH_GC_MS=4000` の間エントリが滞留する=裁定Iが禁じた「作っては壊す」に逆戻り)。
- ★**空きスロットも毎フレーム `seen` に入れる**(監査 C-4)。入れないと `sweepShadowPoolV9`
  (`pixiScene.ts:9196-9209`)が4秒で destroy し、**爆発の間隔が4秒を超えるたびに geometry を作り直す**。
- ★**`fading` 状態は作らない**(v11案の**自己矛盾**を解消): v11 は「追い出したら `fading`」かつ
  「`fading` は再利用しない」と書いており、**両スロットが埋まった所へ強い爆発が来ると
  空きがどこにも無く、一番近い閃光でそのキャラの影が120ms消える**という、回転より目立つ事故になっていた。
  ⇒ **追い出しは即時。ただし追い出してよいのは"見えていないもの"だけ**にする:
  - 新参を**含めて** `falloff × life` を比較し、**新参が最小なら新参を採用しない**
    (v11案は新参を比較対象から外しており、**遠方の弱い爆発が足元の濃い影を叩き出せた**)。
  - ★**既存スロットの現在αが `SHADOW_EVICT_ALPHA_MAX = 0.08` を超えていたら追い出さない**
    (=新参を採用しない)。⇒ **見えている影は決して1フレームで消えない。**
  - 3つ目の濃い爆発が同時に来た場合は**その影が出ないだけ**(ポップは起きない)。
- ★**スロット選択は `src/utils/shadowSlots.ts` の純関数**に切り出し、同コミットでテストを書く
  (CLAUDE.md 実装精度の規律4)。**`SHADOW_GLOW_MIN_DIST_PX` の判定と圏外凍結も同ファイルの純関数**にする。

**S-12-2. 爆発シルエットの幾何(`life` を長さから外す)**
```
falloffRaw = 1 - dist / reach
nearFade   = smoothstep(SHADOW_GLOW_MIN_DIST_PX, SHADOW_GLOW_MIN_DIST_PX × 2, dist)   ★境界のランプ
falloff    = max(0, falloffRaw) × nearFade
lenMult    = 1 + SHADOW_GLOW_STRETCH × min(falloff × SHADOW_GLOW_WEIGHT, SHADOW_GLOW_LEN_CAP)
```
- ★**`SHADOW_GLOW_LEN_CAP = 2.0`**。旧 `SHADOW_GLOW_SUM_CAP` と**同じ値を引き継ぐ**ので最大の伸びは
  `1 + 0.9×2.0 = 2.8倍` で**v9と一致する**(実機で見てきた最大長が変わらない)。定数名だけ変える。
- ★**毎フレーム再計算する**(社長裁定「光源から見て物体が動いたなら動かす。自然の法則に従う」)。
  ⇒ **物体が動けば影は回る。これは仕様。**
- ★**`SHADOW_GLOW_MIN_DIST_PX = 24` の根拠を訂正する**(監査の指摘どおり v11 の根拠は**誤り**だった):
  v11 は「プレイヤー自身の位置に強glowを出す実装が5箇所(`gameStore.ts:5394/5611/6106/6282/8171`)」と
  書いたが、**5行とも `bossFullStunHits` の"ボス被弾位置"**。**プレイヤー位置は
  レベルアップの2発(`:7314`半径150 / `:7315`半径88)だけ**。
  ⇒ **ガードは残す**(レベルアップの2発は実際に足元に湧き、`PLAYER_HITBOX=28` なので中心は足元から約14px
  =24px未満で抑制される)。**ボス被弾glowはボス中心=ボス足元から高さ/2離れており、このガードは効かない**が、
  そちらは「物体と光の位置関係」そのものなので**効かなくてよい**(裁定どおり動いて正しい)。
- ★**境界をランプにする**(監査 C-1): v11 の二値判定だと `dist=23→25` の1フレームで
  **逆向きの2.8倍の影に丸ごと入れ替わる**。上式の `nearFade` で滑らかにする。
- ★**圏外(`dist > reach`)へ出たら幾何を凍結する**: 凍結時点の `dirX/dirY/lenMult/falloff` を
  スロットに保存し以後それを使う。αは `life` に従って落ち続ける。
  ★**圏内へ戻っても凍結は解除しない**(解除すると幾何が飛ぶ)。**その光が死ぬまで凍結のまま。**

**S-12-3. 濃さ** — 上の C 節のとおり。★`SHADOW_GLOW_DARKEN` と `darkMult` は**削除**(死にコード)。

**S-12-4. 消え方**
- **通常**: `life` が 0 へ向かうと α が自然に 0 になる。**専用のフェードアウトは要らない。**
- ★**光が突然消える経路が1つある**: **`effects` 配列の400件上限**で**寿命前の強glowが splice される**
  (`gameStore.ts:13649/13679/13692`)。混戦では実際に起きる。
  ⇒ 参照していた光が候補一覧から消えたら、★**幾何を凍結したまま α を
  `SHADOW_EXPL_FADE_MS = 120ms` で 0 まで落とす**。★**これは「戻る動き」ではない**(αだけ)ので回転しない。
- ★**点く側は即時。フェードインは付けない。** ⇒ 爆発スロットのメッシュは
  **`SHADOW_MESH_FADE_IN_MS`(150ms) の対象外**にする(監査2-5: 通すと**必ず150msかけて出てくる**)。

**S-12-5. 対象と上限**
- ★**静止物(木/壁/プロップ/cityProps/花/建物)も対象に含める**。v9 は既に全キャスターへ

### ★★方式転換: 影は「絵そのもの」から取る(社長指摘 2026-08-02)
> 「見た目に対して圧倒的に細い。ちなみに**オクトラはテクスチャの形で影を取ってる**から、
> **絵をそのまま黒くして、乗算で乗せつつ伸び縮み**ってことになるのでは」

**社長が正しい。オクトラはHD-2Dで、スプライトが3D空間で本物の影を落とす=影の形は絵のシルエット。**
「汎用の塊を焼く」方式は、**どう焼いても絵の形にはならない**ので、原理的に「細い/合わない」が残る。

#### 新方式(これを本線にする)
**アクターのテクスチャをもう1枚、黒くして・寝かせて・乗算で地面に置く。**
- `sprite.texture` をそのまま使う(**焼いたテクスチャは一切不要**)
- `tint = 0x000000`、`blendMode = 'multiply'`、`alpha = ステージのshadowAlpha`
- 足元にアンカー(0.5,1)を置き、**光の向きへ回転 → 長さぶんだけ縦に潰す**
- 長さは今の `shadowLength`(36/32/52)をそのまま使える

#### ★影の長さは「絵の高さ × 比率」にする(社長指摘 2026-08-02「トールとミーミルは実物より小さい」)
社長の推測「始点が一番下のピクセルだから?」は**外れ**。原因は**長さが絵の大きさに関係ない固定px**だから。
**これはモックだけでなく、いまのゲームでも起きている:**

| | 絵の高さ(目安) | 影の長さ | 絵に対する比 |
|---|---:|---:|---:|
| ゾンビ | ~125px | 36〜56px | **0.3〜0.4** |
| ミーミル | 500px超 | **同じ36〜56px** | **~0.1** |

`shadowLength=36`(世界px固定)+ 倍率 `clamp(w/42, 0.7, **1.55**)` の**上限**で、
**大きい物ほど影が相対的に小さくなる**。F-6(幅→高さ)を入れても**clampが効いて頭打ちのまま**。

⇒ **シルエット方式なら自然に直る**: **長さ = 絵の高さ × 一定比率**(=寝かせる角度が一定
=太陽の高さが一定、という物理的に正しい意味になる)。
- 対象によらず同じ比率でよいので、**個体ごとの倍率もclampも要らない**。
- **社長が調整済みの 36/32/52 は「比率」へ読み替える**(相対関係は保つ)。
  絵の高さ〜125pxのゾンビで今と同じ見え方にするなら **昼0.35 / 夜0.31 / cine0.50** 付近が出発点。
- **モックは既定 0.42。スライダーで比率を直接いじれる。**

#### ★接地影をハッキリさせる(社長指摘「足の間が広いキャラだと足から影が伸びてない違和感を減らせる」)
**指摘が構造を突いている。** シルエット影は**1つの足元から1本**伸ばすので、
**トールのように足の間が広いキャラでは、どちらかの足からズレて伸びる**(2本の足それぞれから
影を出さない限り原理的に避けられない)。
⇒ **足元の接地の暗がりをハッキリさせると、そこが「地面に立っている根拠」になり、
伸びた影のズレが気にならなくなる。** 安く効く正しい対処。

**構成(接地影は2段)**:
| 段 | 役割 | カーブ |
|---|---|---|
| **芯** | **ハッキリした接地**(形が出る) | `0→1 / 0.52→0.93 / 0.82→0.40 / 1→0` |
| 外側 | 空気感(にじみ) | ソフトカーブ(既存) |

**合計3枚/体**(接地の芯・接地の外側・シルエット)。全部プール済みスプライト。
**負荷は 1/10 の見込みだが、着手時に `?silshadow=` のA/Bで実測する**(1枚→3枚になるため)。
モックの既定: 伸び0.85 / 足元の絞り34% / ぼかし45% / **接地の濃さ95%**。

#### ★やわらかさは「シルエット自体をぼかす」で作る(社長指摘「にじみ殆ど効いてない」)
下に敷いた楕円は**シルエットに覆われて見えない**ので効きが弱かった。
⇒ **シルエットそのものをぼかす**のが本筋。
**やり方: 黒くした絵を小さく焼いてから拡大する**(縮小→拡大のバイリニアでソフトになる)。
- **焼くのは起動時の1回だけ。実行時は同じ1枚のスプライト。** ぼかしフィルタは使わない(per-pixelパス回避)。
- Pixi では**低解像度の RenderTexture を1枚作って使い回す**(テクスチャごとに1枚・キャッシュ)。
- **ぼかし量 = 縮小率**。モックは「ぼかし」スライダーで 1〜15倍縮小まで。既定45%。
- にじみ(楕円)は**シルエットの外側へはみ出すよう大きく**して残す(既定80%)。**形はシルエット、
  空気感はぼかし+にじみ**、という分担。

#### ★2枚構成にする(社長指摘 2026-08-02「影のグロー感は前の楕円の方が雰囲気ある」「全体的に小さくなった」)
- **グロー感**: シルエットは輪郭が硬いので、**楕円が持っていた"にじみ"が消えていた**。
  ⇒ **接地のやわらかい暗がり(ソフト楕円)をシルエットの下に敷く**=**1体2枚**。
  **オクトラも「接地の柔らかい暗がり」+「投影されたシルエット」の2枚構成**なので、方式としても正しい。
  - **シルエットが"形"、にじみが"雰囲気"**を担当する。にじみは既存の焼きテクスチャ(ソフトカーブ)を流用。
  - 枚数: 今は1体1枚 → **2枚**。プール済みスプライトなので**負荷は 1/10 の見込み**だが、
    `?silshadow=` の A/B と同時に**2枚版も測る**。
- **大きさ**: 比率の既定 0.42 は小さすぎた(旧案の換算ではゾンビの影が絵の3倍あった)。
  **モックの既定を 0.85 に、上限を 1.8 まで拡張。** 実機で社長が決める。

#### ★足元へ絞る(社長指摘 2026-08-02「足元がどうしても接地面矛盾するから、足元ほど細く、
#### 足元の大きさに集束させればいいのでは」)= **その通り**
シルエットをそのまま寝かせると、**接地端の幅＝絵の一番広い所**になり接地面と矛盾する。
実際の投影は「**地面に近いほど細く(足の断面)、離れるほどその高さの断面幅へ広がる**」形。
⇒ **接地端を足元の幅へ絞り、先端で絵の幅になるよう台形に歪める。**

**実装は安い**: **PixiJS 8.19 に `PerspectiveMesh` がある**(4隅の座標を指定するメッシュ)。
- 近い辺(接地) = `footX ± 足元の半幅`
- 遠い辺(先端) = `footX + 向き×長さ ± 絵の半幅`
- **1ドローコール**で台形になる。モックは canvas なので40帯に分けて描いているが、**本番は帯不要。**

★**「足元の幅」の実測がここで戻ってくる**が、用途が変わって**ずっと寛容**になった:
前は「影の形そのもの」を決める値だったが、いまは**接地端の絞り率**だけ。
既定は一律(叩き台 **34%**)でよく、**合わない個体だけ実測値で上書き**すればよい
(裏ボスは測定済み: ミーミル0.33 / トール0.46 / スカディ0.91 / ヨルムンガルド0.95)。

#### この方式で消える問題(下の第1部・第2部の設計の大半が不要になる)

| **F-5 引き伸ばしでぼけ幅が不均一** | 焼いた塊を伸ばしていないので起きない |
| **F-6 長さが幅から決まる** | 絵の高さをそのまま潰すので**自動的に高さ基準**になる |
| **足元幅の実測(0.33〜0.95)** | **不要**。絵から出るので測る必要がない |
| **裏ボスの特別扱い** | **不要**。判定を一切使わない |

#### ★F-6 の具体案: 影の長さの基準を「幅」から「高さ」へ(社長質問「伸びの長さ提案ある?」)

## 4-3. ★なぜ影が見えないのかの答え
オクトラは暗部を思い切り沈めても影が読める。**影が落ちている地面を光が明るくしている**から。
**明るい床の上の黒い影は、暗部を沈めるほどむしろくっきりする。**
うちは **光が地面をほとんど明るくしていない**(glowはキャラの周りに乗るだけ)ので、
暗部を沈めると影も地面も一緒に黒へ行く=**影が見えない**。
⇒ 社長の実機報告「昼のステージ3だけ影が見える」は、**地面が明るいステージだけ条件が揃っていた**ということ。

## 4-4. ★実装の順序(この順でないと意味が無い)
### 手順1(先): **光が地面を明るくする**
これが無いと、パンチを何度直しても影は読めない。**影が乗る"明るい床"を作るのが先。**
- 強glowの位置に、**地面レイヤーへ加算の光だまり**を敷く(既存の `playerGroundPool` と同じ作法=
  焼いたテクスチャ+プール済みスプライト。**per-frame Graphics は使わない**)。
- 半径は光の `radius × 数倍`(影の `SHADOW_GLOW_REACH_MULT=6.25` と桁を揃える)。
- ★**負荷**: pooled sprite 1枚/光。CLAUDE.md の実測どおり「強glowの絵は無料」の側。**投影影を増やさない。**

### 手順2(後): **パンチの作り直し**
`punchGrade` の中身を 4-1 の実測に合わせる。
- **`brightness` の持ち上げをやめる**(0 かマイナス)。全体は明るくしない。
- **暗部を沈める**(25%帯を大きく落とす)。
- **肩(90〜95%)だけ持ち上げ、頂点(99%)は上げない**。
- **彩度を上げる**(`ColorMatrixFilter.saturate`)。
- ★ツマミは既存の `?punchcontrast=` `?punchbright=` を活かし、彩度用に1つ足す。

## ★D-2b. 影の起点を「絵の足元の中央」にする(社長指示 v0.25.2815「縦横両方ね。絵の、ではなく絵の足元の」)
社長「影の起点を足元の真ん中にできる? 基本、絵から少し離れてスタートしてる」。

### 事実
- `bakeSilhouette`(`pixiScene.ts:9081`)は **`src` をそのまま `srcW×srcH` へ縮小して焼く**。
  素材の**透明な余白ごと焼き込まれる**。
- メッシュは**焼いたテクスチャ全体**を台形に貼る ⇒ **余白がそのまま影の根元/左右のズレ**になる。
- D-2 で挙げた縦の余白(jormungand 192px / flower-5,6,7 54〜57px)に加え、**横の寄り**も同じ理屈でズレる。

### やること(★3段目=半影の `bakeSilhouette` 書き換えと同じコミット)
1. **絵の実体bboxを縦横とも測る**(`spriteFootRow`/`spriteTopRow` は縦のみ。**横=左右の実体列を足す**)。
   結果は `textureContentCache` を `{ top, bottom, left, right }` へ拡張して保持。
2. **焼く時に bbox で切り詰める**: `new Texture({ source: src.source, frame: bbox })` を `body` に使い、
   `srcW/srcH` も bbox の寸法にする。⇒ 焼き上がりに余白が入らない。
3. **起点を絵の足元中央へ**: `placeShadowV9` の `footX` を `bbox の横中央`、`footY` を `bbox の下端`へ寄せる
   (どちらも `rawW/rawH` に対する割合で持つ=スケールに追従する)。
4. **長さも絵の実高さで計算**(`rawH × (bottom−top)`)。

### 受け入れ条件
- 余白を持たない素材(610枚)の影が**1pxも変わらない**ことをコードで示せること。
- `flower-5/6/7`・`jormungand`・城で、**影の根元が絵の足元の中央から始まる**こと(実機)。
