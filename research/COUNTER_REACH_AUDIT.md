# カウンター成立域(reach)の全系統監査 — 2026-08-19 / 監査役(Opus)実査

社長ゴール(言葉のまま): 「**(カウンターが)身体に触れているかで見ていて、実際カウンターできない技が
多い気がするので、監査して**」

**この文書は調査・報告のみ。コードは1バイトも変更していない。**
行番号は v0.25.3585(commit 7c7f7ef)時点。判定は全て実装を読んで確認した(推測で埋めた箇所は §5 に「未確定」と明記)。

## 0. 要旨(先に結論)

1. **社長の見立ては正しい。** 賞金首(舞妓を除く)・裏ボス3体・idol・天使の一部で、
   **カウンターの成立域は「ボスの当たり判定の矩形にプレイヤーの矩形が重なっているか」だけ**
   (`rectsOverlap`)。**赤い予告(帯/円)の中に居ることは成立条件になっていない。**
2. **「触れる」は近接が届く距離よりずっと近い。** 近接は `MELEE_RADIUS=74` を**当たり判定の最近点**まで
   測る(`aimEnemyDist2`)。実装コメント自身が「近接の定位置=縁74px+プレイヤー半幅≈10 → 縁から≈84px」
   (gameStore.ts:1973)と書いている。つまり**普通に殴れる位置=縁から74〜84px**。
   一方カウンターは**縁から0px(=めり込み)**が要る。**この60〜84pxの差が「取れない」の正体**。
   - 賞金首(44×44)なら: 殴れるのは中心距離 ≒ 96px まで / カウンターは中心距離 ≒ 36px 以内。
3. **ただし全滅ではない。** 帯/円の攻撃の**大半は当たった瞬間だけ別経路で弾ける**
   (`pumpkinBlasts` に積まれる攻撃は combatTick の**ブラストパリィ**が窓中なら無効化+反撃)。
   これは「命中の1フレーム」しか無いジャストパリィで、**windup/硬直の数百msを使う"技へのカウンター"とは別物**。
4. **例外的に「カウンター手段がゼロ」の技が5つある**(帯/円の中でも取れず、命中の瞬間も弾けない)。
   これが最上位の違反(§4-A)。**馬乗りの狙撃・idolの狙撃・舞妓の毬・アクラシエルの転移衝撃と結晶の槍**。
5. 直近2件の修正(v0.25.3571 馬乗り360/突進・v0.25.3585 舞妓3技)は**同じ穴の個別修理**であり、
   **穴そのもの(=体の重なりを既定の成立域にしている構造)は全系統に残っている。**

### 1-3. reach の形の一覧(現状)
- **体の重なり(`rectsOverlap`)** … 経路3/4/5/6の既定。**これが今回の主題**。
- **帯(`distToBandRect`)** … トール実行3技 / ミゲル払い・突進斬り / ウリ大薙ぎ・振り下ろし・突き /
  スリィエル ビーム・薙ぎ / アクラシエル 放射棘 / 舞妓の薙ぎ(v3585) / ブラストパリィ(カプセル)。
- **自分中心の円** … 馬乗り360度ムチ(v3571) / 舞妓 毬回し(v3585) / スリィエル 回転斬 / アクラシエル 爆発。
- **着地円** … 舞妓 水鳥乱舞(v3585) / 城ボス 飛び掛かり(v2601。ただし**接触も同時に要る**=狭める用途) / ブラストパリィ(円)。
- **無し(カウンター分岐そのものが無い)** … §4-A の5技。

> **参考(事実)**: 城ボスの `inGiantJumpLandingZone`(v0.25.2601)は「赤い円の中でだけ弾ける」という
> **制限**として入っている(接触の代わりではない)。一方 v3571/v3585 の円・帯は「体に触れていなくても
> 赤の中なら弾ける」という**拡張**。**同じ「赤い図形」という言葉で、2つの反対向きの使い方が同居している。**

### 2-6. 城ボス(giantbat・gameStore.ts の `g-*`)
- **windup は意図的にカウンター対象外**(M51受け入れ条件5=W4「予告を出したら必ず実行させる」・
  `GIANT_PARRYABLE_PHASES` のコメント)。対象は**実行中2種(`g-dash-charge`/`g-sweep-active`)と全 `g-*-recover`**。
- 成立域は**全て体の接触**。空中系(`g-jump-air`/`g-trijump-air`/`g-glide-active`)だけ、
  接触に加えて**着地円/滑空帯の中**であることを要求(=狭める側)。
- **全ての `g-*` AoE は `pumpkinBlasts` を経由する**(gameStore 10856/10867/10952/11017/11093/11120/11148/
  11222/11362/11449/11479/11483/11518/11569/11650/11725)。**=命中の瞬間はブラストパリィで必ず弾ける。**
- 判定: **系としては自己整合**(赤い予告=避ける、命中の瞬間=ジャストパリィ、硬直=接触パリィ)。
  ただし `g-sweep-active`(帯)は「帯の中に居ても体に触れていないと弾けない」=帯文法とは不一致(軽微)。

## 3. 数字で見る「触れる」の狭さ(なぜ体感で取れないか)

| 主語 | 体(当たり判定) | 体の重なりに要る中心距離 | 近接が届く中心距離(`MELEE_RADIUS=74`+最近点) | 差 |
|---|---|---|---|---|
| 賞金首4種 | 44×44 | **≤36** | ≒96 | **60px** |
| idol | 40×20 | ≤34(横)/ ≤24(縦) | ≒94 / ≒84 | 60px |
| 天使6体 | 60×30 | ≤44 / ≤29 | ≒104 / ≒89 | 60px |
| トール | 140×70 | ≤84 / ≤49 | ≒144 / ≒109 | 60px |
| ミーミル | 223×124 | ≤125 / ≤76 | ≒185 / ≒136 | 60px |

**プレイヤーは「殴れる位置」に立つ。その位置は、どのボスでも一律に体の縁から約74〜84px外側**であり、
**カウンターに要る「縁から0px」よりちょうど1手ぶん遠い**。だから
「殴りながら合わせているのに取れない」という体感になる(社長の観察と一致)。

### D. 軽微 / 記録のみ
- **馬乗り 突進の windup**(流星ライン420): 実行中は接触で取れるので実害は小さい。werewolf 由来の形。
- **舞妓 手毬打ちの windup/硬直・水鳥乱舞の windup**: 体の重なり。硬直が長いので走り込めば取れる
  (社長が「毱打ちは取れる」と感じているのは、おそらくこの**長い硬直に走り込んだ接触**)。
- **鋏 高速弾の windup/硬直**: `BOUNTY_WINDUP_STATES`/`RECOVER_STATES` に載っているが、直前に190px
  後退した位置なので**体の重なりは構造的に起こらない**=事実上の死に項目(害は無いが、リストが
  「載っている=取れる」という誤読を生む)。
- **城ボス `g-sweep-active`**: 帯の中でも接触が要る(帯文法と不一致)。ただし命中の瞬間はブラストパリィで弾ける。
- **設置系ハザード**(スカジ氷塊/氷檻・ジブリルの火/聖別・ラフィ骨刃): 赤い予告を持つが、
  「置かれた物」であってボスの技の局面ではない。**カウンターできるべきかは仕様判断**(§5)。
- **アクラシエル転移の描画と判定が別フィールド**: 描画は `AC_T.spear.radius`(pixiScene 16178)、
  判定は `AC_T.warp.impactRadius`(angelBossTick 2480)。**今は偶然どちらも92**だが、
  ボスメーカーで片方だけ動かすと「赤いのに当たらない/赤くないのに当たる」になる(潜伏バグ)。

## 5. 未確定(推測で埋めなかったもの)

1. **設置系ハザードをカウンター対象にすべきか**は仕様判断であり、監査では決めない。
   事実だけ: **スカジの氷塊は `pumpkinBlasts` 経由で弾ける / アクラシエルの結晶の槍は弾けない**。
   同じ「置いて2秒後に赤円で起爆」なのに**扱いが割れている**(=どちらかに揃える必要がある、という指摘まで)。
2. **ブラストパリィを「カウンター」と数えるか**。実装上は Counter! 表示・確定クリ反撃・CDリファンドまで
   同一なので**プレイヤーからは同じもの**に見える。ただし**成立できる時間が1フレーム**なので、
   本監査では「技へのカウンター」とは別枠として扱った。この線引き自体は社長裁定の対象。
3. **狙撃(A-1/A-2)を「カウンターで返せる技」にするか、「線から出るだけの技」にするか**は
   **仕様変更**(体験が変わる)。監査としては「**赤い帯を出しているのにカウンター手段が皆無**」が
   文法違反である、という指摘まで。どちらへ揃えるかは社長判断。
4. **賞金首 `bb-quickshot` の死に項目**を消すか残すかは無害な整理なので優先度は最低。
5. **ジブリルのランス(ビーム140ms)** は実行中の帯reachが無いが、**ビームの持続が短く**、
   実機で「赤い帯の中に居られる時間」が体感どれだけあるかは未計測。実機確認が要る。
6. 本監査は**プレイヤー側のみ**。守護霊(ゴースト)の請求経路は同じ州リスト・同じ `thorBodyOverlapNow` /
   `bodyOverlapNow` を共有しているため、**reach を直すと自動的にゴースト側も同じ形になる**
   (=プレイヤーと守護霊の非対称は生まれない)ことだけ確認した。

## 6. 直し方の型(参考・実装はしない)

v0.25.3585(舞妓)が既に確立している形をそのまま横展開できる:

```
// bountyTick.ts 1944-1959 と同じ構造 = 「州ごとに reach の図形を選ぶ」
if (州 === 帯の技) inReach = distToBandRect(player中心, aiFrom, aiTarget, halfWidth) <= pRad;
else if (州 === 自分中心円の技) inReach = hypot(player中心 - ボス中心) <= radius + pRad;
else if (州 === 着地円の技) inReach = hypot(player中心 - aiTarget) <= radius + pRad;
else inReach = rectsOverlap(ボス矩形, player矩形);   // 従来の既定
```

**寸法は必ず技のテーブル(bountyScript/hiddenBossScript/angelScript/idolScript)の同じ場所を読む**
=描画・判定・カウンターの3つが1つの数字を見る(「赤いのに当たらない」の再発防止)。

**恒久化の提案(監査役の推薦・採否は社長)**: 「**赤い図形を持つ技は、その図形が
カウンターの成立域でもある**」を `constitution.test.ts` の不変条件として機械化する。
今回の10件は全て「新しい技を足す時に reach を書き忘れた」もので、**人の注意では3度目の再発を止められていない**
(v3571・v3585・本監査で3回目)。
