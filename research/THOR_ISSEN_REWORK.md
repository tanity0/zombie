## 1. 一閃の台本(2段固定)

一閃は**毎回この2段**で出る。段の間に空き時間を置かない(連続)。

```
[段1] 無の境地 300ms  紫の円(近距離)・何もしない・カウンター不可
        └─ 円の中でプレイヤーが近接を振った ⇒ 即・段2の実行へ(必中一閃)
[段2] 一閃     500ms  赤の帯(310×160)・従来どおりカウンター可
        └─ 予告満了 ⇒ 従来のダッシュ(dashMs 280)→ issen-recover
```

### 1-1. 段1「無の境地」(紫・円・近距離)

| 項目 | 値 | 種別 |
|---|---|---|
| 州名(bossState) | `issen-nihil` | 確定(§5-1に理由) |
| 予告時間 | **300ms** | 社長指定=確定 |
| 判定の形 | **円**(中心=トールの当たり判定矩形の中心) | 裁定2=確定 |
| 半径 | **200px** | **叩き台** |
| 色 | 紫(既存のミーミル・レーザーと同じ紫系: 塗り `0x9333ea` / 縁 `0xc084fc`) | 確定(文法) |
| ダメージ | **なし**(この州はプレイヤーに一切ダメージを与えない) | 確定 |
| カウンター | **不可**(紫の文法。体が重なっていても成立させない) | 確定 |

- 半径200pxの根拠(叩き台): ナイフの間合い `MELEE_RADIUS=74` + トールの体の半幅70 ≒ 144、
  鞭の射程150 + 半幅70 ≒ 220。**「殴れる位置=紫の中」**にしたいので、その間を取った丸い数字。
  実機で「近づいたら振れない」圧が出る値へ寄せる。
- **円は「振るな」の合図**であって立ち入り禁止ではない。中に居るだけでは何も起きない。
- **赤いフラッシュを出さない(監査⑧)**: `thorFlashTint`(`pixiScene.ts`)は
  「ダメージの瞬間の**400ms前**から体を赤く鋭く点滅」させる演出。紫の段は**300ms**しかないので、
  同じ式を通すと**紫の間じゅう体が赤く光る**=「赤=危険/カウンター対象」の文法と真っ向から食い違う。
  よって **`issen-nihil` では `thorFlashTint` を呼ばない**。体のティントは**紫**(`0xc084fc` 寄り)を
  使い、赤フラッシュは**段2(赤予告)の残り400ms**からだけ出す(=現行の意味「ダメージの瞬間の前」を保つ)。
- **慣性(MUST)**: 円は出現時に半径 0→1 を ease-out(叩き台120ms)で開き、消える時は ease-in で
  縮めながらフェードする。**パッと出てパッと消えるのは禁止**(CLAUDE.md「動きの絶対ルール」)。
  トール本体は静止ではなく**息を詰める**予兆(既存 `windupTremorPx` の震えを紫段でも使う=
  型を発明しない)。
- **動きは大きく**: 円の縁は既存の帯予告(`drawTelegraphBand`)と同じ濃さ以上で描く。薄い紫は
  「出ていない」のと同じ。

**受け入れ条件(段1)**
1. `issen-nihil` 中に**プレイヤーがどのような接触をしても**ダメージが発生しない(体の重なりも含む)。
2. `issen-nihil` 中に**カウンターが成立しない**(近接を振っても青いCounter!演出・反撃ダメージ・
   counter-leap のいずれも出ない)。→ 出る場合は§5-2の配線漏れ。
3. 描いてある紫の円の半径と、必中の引き金に使う円の半径が**同じ1つの定数**から来ている
   (`HIDDEN_THOR_TUNING.issen.nihilRadius`)。片方だけ動く実装は不可。
4. 300ms 経過で必ず段2(`issen-windup`)へ進む。ここで `chase` へ戻る経路が存在しない。
5. 円の出現・消滅に加減速がある(1フレームで最大サイズにならない)。
6. **紫の300msの間、体が赤く光らない**(`thorFlashTint` が呼ばれていない)。赤フラッシュは
   段2の残り400msからのみ出る。

### 1-2. 段2「一閃」(赤・500ms・従来のダッシュ)

| 項目 | 値 | 種別 |
|---|---|---|
| 州名 | `issen-windup` → `issen-dash` → `issen-recover`(既存のまま) | 確定 |
| 予告時間 | **500ms**(旧2400) | 社長指定=確定 |
| ダッシュ | `dashMs 280` / `range 310` / `halfWidth 80` / `recover 900` | **不変**(触らない) |
| 予告の絵 | 従来どおり赤の帯+流星の描き→消し(`meteorPhase`+`drawTelegraphBand`) | 確定 |
| カウンター | **従来どおり可**(裁定1) | 確定 |

- 狙いのロックは**段1の開始時**(`beginThorMove('issen')` と同じ処理)に1回だけ行い、段2で
  ロックし直さない。段1の300msも含めて「もう振り向かない」=居合の型を保つ。
- **段2に入った瞬間、赤の帯が0からではなく既に張り詰めた状態で出る**のは避ける。既存の
  流星文法(`prog` 0→1)をそのまま500msへ縮めて使う=絵の入りに慣性が残る。

**受け入れ条件(段2)**
1. 赤い帯の図形と `issen-dash` の当たり判定(`distToBandRect` 310×80)が**一致**する
   (現行の一致を壊していない)。
2. 予告500ms・ダッシュ280ms・硬直の値が台帳(`HIDDEN_THOR_TUNING`)から読まれている
   (pixiScene 側に数値の複製が増えていない)。
3. `issen-windup` 中のカウンター成立が**赤帯で**起きる(§8-2の裁定=帯へ揃える。他ボスと同じ宣言表に乗せる)。

### 1-3. 必中一閃(紫の円の中で近接を振った時)

**引き金**: 州が `issen-nihil` の間に、**プレイヤーが近接攻撃を振り**、その瞬間に
**プレイヤーの中心がトールの紫円の内側**にあること。

**結果**: 残りの紫予告と**段2の赤予告500msを丸ごと捨てて**、その場で `issen-dash` へ入る。
狙いは**引き金の瞬間のプレイヤー中心**へ**取り直す**(段1でロックした向きは使わない。
振ってきた相手を斬るため)。ダッシュ自体(280ms・310px・半幅80)は通常の一閃と同じ。

- **カウンター不可(★配線を明示する。宣言だけでは破れる)**: 即発動の `issen-dash` は紫の文法を
  引き継ぐ=この一撃はカウンターできない。プレイヤーは**近接の振り硬直中に斬られる**(=「つまり必中」)。
  **ところが現行のままでは逆に「ほぼ確実にカウンターされる」**——実在確認した事実:
  - `issen-dash` の被弾解決(`useGameLoop.ts` 6311-6317)は**帯に触れた時点で
    `Date.now() <= cp.counterWindowEnd` を見て、開いていればカウンター成立**にする
    (windup州だけにカウンター経路がある、ではない。**実行中の帯にも経路がある**)。
  - 引き金である近接スイングの確定は、**同じ tick で `counterWindowEnd` を開く**
    (gameStore 6775=ナイフ / 6304=刀 / 6330=鞭)。
  - つまり「振った瞬間に即発動」させると、**その振りが開けた窓で必ず弾かれる**=必中の逆。
  - **確定仕様**: 即発動時に `Enemy.issenGuaranteedUntil`(= `issen-dash` の終了 gameTime)を立て、
    立っている間は **6313の `counterWindowEnd` 分岐をスキップして `damagePlayer` へ直行**する。
    ゴースト/守護霊側の帯ヒット(`applyGhostAllyCapsuleHit`)は現行どおり(対プレイヤーの
    カウンター経路だけを閉じる)。通常の一閃(赤経由)では**このフラグを立てない**
    =従来どおりカウンターできる(裁定1)。
  - フラグは `issen-dash` を抜ける時(recover/chase/カウンター以外の中断)に**必ず落とす**
    (立ちっぱなしで次の一閃までカウンター不能にしない)。
- **「必中」の実装は判定を消すことではない**。狙いを振った相手へ取り直すので、近接の間合い
  (紫円の内側)に居る相手は帯の中に入る=**幾何的に当たる**。当たり判定は従来の帯のまま
  (見たまま=帯の外の第三者には当たらない)。
- **慣性(MUST)**: 即発動でもダッシュの加減速カーブは通常の一閃と同一。ワープに見せない。
- **1回だけ**: 1つの `issen-nihil` から即発動できるのは1回(2重発火の防止)。
- 演出: 紫の円は即発動と同時に**縮めて消す**(ease-in)。斬撃そのものの絵は既存の一閃と同じ
  (`latchFx` 経由で最後まで描き切る)。

**「近接を振った」の定義(監査⑦への回答=確定)**
- 判定に使うのは**その tick でプレイヤーが近接スイングを確定させた事実**であり、
  `player.meleeSwingAt` を**そのまま読んではいけない**。理由(実在確認済み):
  - `markMeleeSwingFx()` が `meleeSwingAt` を書く経路は**9箇所**(+ useGameLoop 2413 の
    アダプタ受け渡し1件)。内訳: **カウンター成立=7箇所**(useGameLoop 5502=トール /
    5566=裏ボス3体 / combatTick 312・748・1189 / angelBossTick 231=天使 / bountyTick 395=賞金首 /
    idolTick 311=アイドル ※この7つは全部「青いCounter!演出」の一式)、
    **追撃=1箇所**(gameStore 4139=スラッシャー追撃)。
    そのまま読むと「**カウンターしたら必中一閃が出る**」という誤発火になる。
  - `counterWindowEnd` の打刻も引き金に使えない。**武器庫サークルでショップを開いた時**にも
    同じフィールドが開く(gameStore 6278)=近接を振っていないのに引き金が引ける。
- **採る形(規則)**: **プレイヤーの近接スイングが確定する箇所すべて**に、**専用の打刻**
  (`player.meleeSwingCommitAt`)を1本立てる。**行番号で列挙した4件は現時点の実例であって
  仕様ではない**——将来ナイフ系の武器や新しい振り方が増えたら、**そこにも打つのが規則**
  (打ち忘れは「新しい武器だけ必中一閃が出ない」という無音の穴になる)。
  - 現行の実例4件: ナイフ=`gameStore` 6775 / 刀=6304 / 鞭=6330 / スラッシャー追撃=4139経路。
  - **打たない**: ショップ経路(6278)/ カウンター成立の演出(上の7箇所)/
    守護霊・分身・幻影の攻撃(社長の言葉は「近接攻撃すると」=プレイヤーの操作)。
  - **経路数を固定する純関数テスト**を同コミットで置く: 打刻を書く関数を1本の純関数
    (例 `stampMeleeSwingCommit`)にまとめ、**それを呼ぶ箇所の数**をテストで固定する
    (ソース走査 or 呼び出し口の集約 + 件数アサート)。増減したらテストが落ちて
    「新しい近接に打刻を足したか?」を人に問う=`ghostTelegraph` の完全性検査と同じ型。
- **時計を混ぜない(実バグ級)**: 打刻は `Date.now()` 系、州の残り時間(`bossStateUntil`)は
  `gameTime` 系。**同じ式で引き算しない**。引き金は「`meleeSwingCommitAt` が前フレームから
  進んだか」のエッジで見る(絶対時刻の比較をしない)。同型の事故が v0.25.3721(フィル+トール)で
  出ている。

**受け入れ条件(必中一閃)**
1. 紫円の内側でナイフ/刀/鞭/スラッシャー追撃を振ると、**その tick で** `issen-dash` に入る。
2. 紫円の**外側**で振っても発動しない(300ms満了後に通常の赤予告へ進む)。
3. **カウンター成立(青演出)では発動しない**(`markMeleeSwingFx` 経由の打刻を読んでいない証明)。
4. **武器庫サークルでショップを開いても発動しない**。
5. 即発動した一閃は**カウンターできない**。根拠は「windup を経ていないから」**ではない**
   (`issen-dash` の実行中の帯にも `counterWindowEnd` を見るカウンター経路がある=6311-6317)。
   **`issenGuaranteedUntil` が立っている間、その分岐をスキップして `damagePlayer` へ直行する**
   ことで閉じる。テスト: 紫円の中で振った直後にカウンター窓が開いていても、
   青いCounter!演出・反撃ダメージ・counter-leap が出ずに**プレイヤーが被弾する**。
9. 通常の一閃(赤予告を経たもの)は `issenGuaranteedUntil` が立たず、**実行中の帯でも
   従来どおりカウンターできる**(裁定1の後半を壊していない)。
10. `issen-dash` を抜けた後に `issenGuaranteedUntil` が残っていない(次の技がカウンター不能に
   ならない)。
6. 引き金の瞬間にプレイヤー方向へ狙いが取り直され、帯がプレイヤーを含む。
7. 1つの `issen-nihil` で発動は**1回だけ**(同フレームに2回 `issen-dash` を書かない)。
8. ダッシュの速度カーブ・所要時間は通常の一閃と**同一**。

## 2. 突き(tsuki)

| 項目 | 現行 | 新 | 種別 |
|---|---|---|---|
| 予告 | 1000ms | **1100ms** | 社長指定=確定 |
| 帯の長さ(range) | 240 | **300px** | 社長指定=確定 |
| 帯の幅 | 全幅30(halfWidth 15) | **全幅30(halfWidth 15=現行のまま)** | 確定 |
| 実行(ms)/追従(trackFrac)/硬直 | 180 / 0.5 / 600 | **不変** | 触らない |
| 溜め中の予告 | **なし** | **赤の帯 300×30 を出す**(裁定3) | 確定 |

**赤帯の描き方(裁定3の実装)**
- 帯は**その瞬間の狙い**から組む: 始点=トールの中心、終点=`(中心) + (遅延追従中の狙い点への
  単位ベクトル) × range(300)`。**狙い点そのものを終点にしない**(狙い点はプレイヤー位置=
  射程より近い/遠いことがあり、実行時に作られる帯とズレる)。
- 溜め中は `trackFrac 0.5` で狙いが**遅れて追う**ので、帯も**毎フレーム描き直す**
  (=見たままが「今の狙い」)。実行(`tsuki`)に入った瞬間に方向が確定し、以降は固定。
- 既存の一閃/払いと同じ**流星の描き→消し**(`meteorPhase`+`drawTelegraphBand`)で統一する。
  新しい意匠を発明しない。
- 400ms前の体の赤フラッシュ(`thorFlashTint`)は現行どおり残す。

**受け入れ条件(突き)**
1. 溜め中に描かれる帯の矩形と、実行(`tsuki`)の当たり判定の矩形が**同じ式**で作られている
   (長さ=`tsuki.range`、半幅=`tsuki.halfWidth`、始点=ボス中心)。
2. 溜め中に狙いを動かす(プレイヤーが横へ走る)と、帯も遅れて追う。**追従が止まった瞬間=実行**。
3. 帯の長さ300・全幅30が台帳の値からのみ来ている(pixiScene に 300/15 の直書きが無い)。
4. ボスメーカーで `tsuki.range` を動かすと、**予告の絵も判定も同時に**変わる。
5. 予告1100ms・実行180ms・硬直の時間は変わっていない(実行と硬直は本件の対象外)。

## 4. 新技「突進」と、その起点の連携「突進 → 突き → 突き」

**社長裁定(2026-08-21)**: 「突進持ってないんだっけ? 突進足して。ミゲルと同じ様なやつ。で、突 突 を付けて。」

**この裁定で§8-3の問題は消滅した**。当初案は「突き起点の台本を新しくする」形だったが、トールの起点は
**既に4本すべて埋まっている**(実在確認 `bossChoreography.ts:45-48`: `issen`/`tsuki`/`harai`/`jump`)ため、
新台本を入れるにはどれかを潰す必要があった。**新技=新起点を足せば、既存4本を1本も触らずに済む**
——社長が避けていたのはこの上書きである。

### 4-1. 新技「突進」(dash・ミゲル型)
- **形**: ミゲルの突進と同じ(溜め → 直進で突っ込む → 打撃 → 硬直)。

## 8. 裁定(全件裁定済み・未決なし)

### 8-1. 一閃の反応時間(赤500ms)= **裁定済み**(社長「一旦それで」)

- **確定**: **500msのまま実機で見る**。帯の半幅(80)も触らない。
- 事実として: 台帳コメントに「半幅80+自機14=94px → **必要900ms**」という反応時間の見積もりが
  ある(v0.25.3461で3000→2400へ縮めた時の根拠)。500msでは**帯の外へ走って逃げるのはほぼ不可能**で、
  答えは「カウンターで返す」へ寄る。紫300msが「来る」の予告として先に立つので**実質の読み時間は800ms**。
- **実機で見る点**: 一閃が「避ける技」ではなく「カウンターする技」になって手応えが成立しているか。
  ここが崩れていたら、半幅か500msのどちらを動かすかを改めて裁定にかける(**先回りして絞らない**)。

### 8-2. 赤い予告中のカウンター成立域(帯か体か)= **裁定済み**(社長「赤いのにカウンターできないは聞くまでもなく直すでしょ」)
- **事実**: 確立済みの文法は「**赤い予告の図形=カウンターの成立域**」(v0.25.3591の是正)。
  ところが**トールだけは宣言表を通らず**、`issen-windup` / `tsuki-windup` / `harai-windup` は
  **体の重なりのみ**で成立する(実行中だけ帯)。実在確認: `hiddenBossCounterableNow`(useGameLoop:5814)が
  `boss.type !== 'thor'` でトールを除外している。
- **確定: 本バッチで揃える**。トールの溜め中のカウンター成立域を、他ボスと同じ**赤い予告帯でも成立**
  する形へ直す。CLAUDE.md「**赤い予告そのものは判定と厳密に一致させる(この一致だけは妥協しない)**」の適用。
  「別バッチにしたい」という当初の推薦は撤回(社長裁定が優先)。§7-5の「意図して残す不一致」の宣言も**削除**。
- **実機で見る点**: 成立域が広がる=**トール戦の難度は下がる方向**。下がりすぎていないかを実機で見る。
- **受け入れ条件**:
  1. `issen-windup` / `tsuki-windup` / `harai-windup` / **`dash-windup`(新技)** の各赤帯で
     カウンターが成立する(帯の図形=成立域)。
  2. **必中一閃(`issenGuaranteedUntil` 中)は引き続きカウンター不可**(§1-3の裁定と衝突しない)。
  3. **他ボスの挙動が1つも変わらない**(除外条件の撤去がトール以外へ波及していない)。
  4. `isBossCounterableNowApprox`(語尾判定)・`ghostTelegraph`・`botSkill` の帯脅威と整合する。

### 8-3. 新技「突進」の追加で解決 = **裁定済み**(社長「突進足して。ミゲルと同じ様なやつ。で、突 突 を付けて」)

### 9-1. 突進の抽選重み(§4に指定なし)
- **問題**: §4は「突進が単発でも台本でも出る(`pickThorMove` の抽選に加わる)」を受け入れ条件にしているが、
  距離帯ごとの**重み**が書かれていない。重みを入れないと抽選に参加できない。
- **入れた値(叩き台)**: `dash: { melee: 0, near: 0, mid: 20, far: 55 }`
  = **スカジの突進の行をそのまま流用**(`skadiScript.SKADI_MOVE_WEIGHTS.dash` と同値)。
- **これで何が変わるか(事実)**: 遠距離の抽選に突進が入るぶん、**一閃(far:70)と突き(far:30)の相対頻度が下がる**
  (far の総重みが 100 → 155)。近距離(melee/near)の読み合い=一閃/突き/払いの配分は**1つも変わらない**。
- **裁定が要る点**: 「遠距離で一閃が減る」のは狙いどおりか。**一閃は決闘の看板**なので、
  減らしたくないなら突進の far を下げる(例 30)か、突進を mid 専用にする案がある。

### 9-2. 突進の斬り抜けカプセルの寸法(§4に指定なし)
- **問題**: §4-1は windup/moveMs/strikeMs/recover/cdMs しか与えていない。到達時の**斬り抜けの帯**の
  長さと半幅が無い。
- **入れた値**: **トールの払い(`harai.range`=310 / `harai.halfWidth`=40)を流用**。
  根拠は「ミゲル型」の型そのもの——ミゲルの踏み込みも `MG_T.harai.range/halfWidth` を流用している
  (`angelBossTick.ts` の mdash-move)。**別欄は作っていない**(ボスメーカーで払いを動かすと突進も動く)。
- **裁定が要る点**: ミゲルの払いは range 190、トールの払いは range 310。**同じ流用ルールでも
  トールの斬り抜けの方が1.6倍長い**。長すぎるなら専用欄(`dash.range/halfWidth`)を新設する。

### 9-3. 突進の溜め中のカウンター成立域(§8-2の受け入れ条件1と§4-1の記述が読み分かれる)
- **事実**: §4-1は「予告=**赤の流星ライン**(突進系の既定文法=**裏ボスダッシュ/ミゲル踏み込みと同じ作り**)」。
  §8-2の受け入れ条件1は「issen-windup / tsuki-windup / harai-windup / **dash-windup(新技)** の
  **各赤帯**でカウンターが成立する」。
- **入れた値**: **`'hidden:thor-dash-windup': 'body'`**(=既存の全突進と同じ)。理由は§4-1が名指しした
  2つの前例がどちらも 'body' だから(`'hidden:dash-windup': 'body'` / ミゲルは `bodyOverlapNow`)。
  流星ラインは**判定を持つ図形ではない**(判定は突進の体そのもの)ので、帯にすると
  「赤くないのに当たる/赤いのに当たらない」ではなく**「予告線の上に立っただけでカウンターが取れる」**
  という別の非対称が生まれる。
- **裁定が要る点**: §8-2の受け入れ条件1を「dash-windup も帯で取れる」と読むなら、
  **全突進(裏ボス3体・ミゲル・馬乗り)を一緒に変える話**になる(トールだけ帯にすると文法が割れる)。
  → **これはトール1体の話ではないので、ここで止めて社長へ**。
