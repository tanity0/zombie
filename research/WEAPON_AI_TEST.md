# 全武器 AI 実機テスト(設計)— 社長指示2026-09-07「全武器ai実機テスト回したいので設計書いて」

## §0 これは何のための道具か / ★何のためではないか

**目的**: **ユニーク武器21挺+サブウェポン「金環」が、実際に動いているかを AI(ボット)に確かめさせる。**

**★これは「強さのバランスを測る道具ではない」**(そこを外すと道具の形が変わるので先に書く):
- 強さの枠は **±10%の帯**を **§5 / §5-2 の式**で既にテストに固定してある。**AIに測り直させない。**
- **DPSの上下・体感の強い弱いは対象外。**
- **綺麗な絵かどうかも対象外**(未支給の素材が6挺ぶんある)。
- **ボスの仕様・ステージの仕様も対象外。**

**⇒ 見るのは1つだけ: 「社長が仕様に書いた言葉が、動いている画面で起きているか」。**

## §1 なぜ要るか(この案件で実際にすり抜けた形)

この案件(v0.25.4118〜4185)で監査が捕まえた **(A)級の指摘は合計27件**。**その分類が、そのままこの道具の
設計要件になる。**

| 形 | 実例 | ユニットテストで捕まったか |
|---|---|---|
| **★1. 仕様の言葉がコードのどこにも無い** | 錬金砲の「範囲が増加」(半径は**絵にしか**使われていなかった)/ 錬金砲の「石が3段階成長」(**石が画面に一切出ていなかった**)/ シグナルの「高い体勢値削り」(**削りゼロ**)/ シグナルの「移動先を予測して置く」(**レティクルが吸い付いていた**)/ コイルの「再収束」(**一度も収束していなかった**) | **全部すり抜けた。**typecheckも帯のテストも通っていた |
| **2. 既存の部品を、前提が違うまま借りた** | 誘導の旋回速度(弾速が3.5倍違い**旋回半径141px>射程140px**)/ ガンブレードの近接を**弾**で作る / アイレーザーのパルス周期を `Weapon` に持つ(HUDが60回/秒再描画) | すり抜けた |
| **3. 慣性を入れる修正が、別経路で慣性を壊す** | 氷槍の床が**点滅**(`createdAt` 上書き)/ 火炎放射器が**脈動**(猶予20ms)/ ロケランが**ease中に反射されて停止** | すり抜けた |
| **4. 経路の取りこぼし** | splashキルで**強個体のクレートが落ちない**(シグナルは全キルがsplash)/ ガンブレードのキルで**通貨が落ちない**/ 守護霊の**空撃ち**/ PC入力で**シグナルが1発も撃てない** | すり抜けた |
| 5. 数えていない | **レールガンが1挺まるごと未実装**だった(バッチCを3+3に割って7挺目を落とした) | 機械的な照合で発覚 |

**⇒ 1〜4はどれも「実際に動かして観測する」でしか捕まらない。**そのための道具。

## §2 2層に分ける(★どちらが何を捕まえるかが違う)

| | 層1 **ヘッドレス走査** | 層2 **実機(ブラウザ)走査** |
|---|---|---|
| 走らせ方 | vitest + `playtestDriver`(既存)。**描画しない** | Playwright + Chromium(`TEST_HANDOFF/HEADLESS.md` の手順) |
| 速さ | **1挺あたり数秒**(60fps換算の時間を数秒で回す) | **1挺あたり実時間30〜60秒** |
| 捕まえられる | **形1の「判定側」**(石が付くか・範囲に入るか・体勢が削れるか)/ **形4**(ドロップ・弾薬・経路)/ クラッシュ・状態の残留 | **形1の「見え方」**(石が見えるか・レティクルが吸い付くか)/ **形3**(点滅・脈動・瞬間消滅)/ 絵の化け |
| 捕まえられない | **見え方は一切分からない**(`pixiScene` を通らない) | **遅い・不安定**(タイミング依存で偽陽性が出る) |
| 実行 | **CIで毎push**(安い) | **社長の指示があった時だけ**(高い) |

★**層1だけでは、この案件で一番多かった「形1」の半分(見え方)が丸ごと抜ける。**
★**層2だけでは、遅すぎて全22件を毎回は回せない。**⇒ **両方いる。**

## §3 層1(ヘッドレス走査)の設計

### 3-1. 既存の何を使うか(★新しく作るものを最小にする)
| 使うもの | 在処 | 備考 |
|---|---|---|
| ボット本体 | `src/utils/playtestDriver.ts` `runPlaytestTick` | ペルソナ/腕前/目的を引数で選べる |
| 走行の器 | `src/store/playtest.test.ts` の `runOnePlaytest` | ★**フェイクタイマーで `Date.now()` を `gameTime` に同期させる処理が要る**(これが無いとノックバック免疫窓・カウンターCD・ヒットストップが全部詰まって近接が機能しない=実測済みの落とし穴)。**この器を再利用する**(書き直さない) |
| 計測 | `src/utils/botTelemetry.ts` | ダメージのチャネル別集計・クリ・近接スイング・サブ使用が既にある |
| 武器の強制 | `useGameStore.grantWeapon(key)` + `setActiveWeapon(id)` | ★**ヘッドレスでは動く**——`resolveSlotKeyNow` は装備設定が空なら**キーをそのまま返す**(`weaponSlot.ts`)。**ブラウザでは装備設定に引き戻される**ので層2では別の手が要る(§5-2) |

### 3-2. 新しく作るもの(1つだけ)
**`src/store/weaponAiTest.test.ts`(仮)**: 22件を1挺ずつ回し、**§4の受け入れ表**を assert する。
- **1件 = 1テスト**(落ちた時にどの武器かが一目で分かる)。
- **走行時間は1挺 60秒相当(3600tick)**を既定にする(短すぎると「たまたま撃たなかった」で偽陰性)。
- **★観測は「0か非0か」を基本にする**(数値の大小を条件にしない=バランス調整で落ちる網にしない)。
- **シード固定**(`wanderSeed` を挺ごとに固定)=**同じ結果が再現する**。

### 3-3. ★観測の入口(足りないものを1箇所に足す)
既存 `botTelemetry` は**チャネル別の合計**しか持たない。**武器ごとの検証には「その武器が何をしたか」の
細かい数え**が要る。⇒ **`botTelemetry` に薄いカウンタを足す**(テスト時だけ動く形にはしない=
**本番と同じ経路で数える**。分岐を増やすと「テストでは通るのに実機で違う」を作るため)。

足すカウンタ(例): `projectilesSpawned` / `explosions` / `beamPulses` / `postureBroken` /
`stonesAttached` / `stoneDetonations` / `cratesDropped` / `currencyDropped` / `ammoConsumed`。
**★どれも「起きた回数」だけ。**位置や大小は持たない(台帳を太らせない)。

## §4 ★受け入れ表(社長の言葉 → 機械で見える信号)

**これがこの設計の本体。**「クラッシュしない」ではなく、**仕様の言葉ごとに1本ずつ信号を置く。**
**全挺に共通の3件**を先に置き、そのあと**武器ごとの固有条件**を置く。

### 4-1. 全22件に共通(これが落ちたら武器が死んでいる)
| # | 条件 | なぜ |
|---|---|---|
| C1 | **その武器で与えたダメージ > 0** | 「装備したのに何も起きない」を捕まえる |
| C2 | **キルが1回以上あり、そのキルで 経験値・通貨 が落ちている** | **ガンブレードで実際に通貨が落ちていなかった** |
| C3 | **ラン終了後、その武器由来の状態が全部消えている**(弾・線・床・石・予約) | **前ランへの持ち越しが実際に3件あった** |

## §5 層2(実機ブラウザ走査)の設計

### 5-1. 手順の正本は `TEST_HANDOFF/HEADLESS.md`
**新しい起動手順を発明しない。**あの文書に**関門の潰し方(localStorage を先に仕込む)**と
**Chromium の起動オプション**(`executablePath: '/opt/pw-browsers/chromium'` / `--use-gl=swiftshader`)が
確立済みで、**毎回ここでつまづく**と明記されている。

### 5-2. ★武器の強制はブラウザでは方法が違う
**`grantWeapon` はブラウザでは使えない**——`resolveSlotKeyNow` が**装備設定に引き戻す**ため。
⇒ **localStorage に ①装備設定(該当スロット=対象キー)②解放状態 を先に仕込んでから開く。**
**既存の `?unlockall=1` と 開発用の「武器解放」トグル**がその口。

### 5-3. 何を撮るか
**1挺につき3枚**。**枚数を増やさない**(`TEST_HANDOFF/results/` にPNGを撮り貯めない=リポジトリを
重くしない掟)。
1. **撃っている瞬間**(弾・扇・線・予告が出ているか)
2. **当たっている瞬間**(命中の絵・数字)
3. **その武器固有の状態**(錬金砲=石が頭上に見えるか / アイレーザー=照射中 / 金環=2本展開 / ロケラン=溜め中)
★**3枚目が本命。**「石が画面に一切出ていない」は**この1枚でしか捕まらない。**

### 5-4. ★機械で見る部分を残す(目視だけにしない)
**社長が見るのは3枚のPNGだけ**にしたいので、**「絵が出ているか」の一次判定は機械でやる**:
- **その武器のテクスチャが読み込まれているか**(`pixiTextures` の解決結果)
- **描画オブジェクトの数が0でないか**(石のマーカー・線・扇)
- **コンソールエラーが0か**
⇒ **落ちた項目だけを社長へ上げる。**全部緑なら「22件緑」の1行で済ませる。

## §9 ★未決(社長の裁定が要る)

- **#T1「層2(実機ブラウザ)を作るか、社長の目視に任せるか」**
  - **(a) S1+S2 だけ作り、見え方は社長の実機確認に任せる。** **推薦**——見え方の網は
    「何が起きるか」を知ってから編む方が当たる。実際、この案件の見え方の事故(点滅・脈動・
    石が出ない・レティクルの吸い付き)は**どれも監査がコードを読んで見つけた**もので、
    スクショの自動比較で見つかる形ではなかった。
  - (b) S1〜S4 を全部作る。
  - (c) 層2だけ作る(層1は既存のスモークで足りるという判断)。
- **#T2「走行時間」**: 1挺60秒相当を既定にしたが、**短いと偽陰性・長いとCIが遅い**。
  **推薦=60秒で始めて、偽陰性が出た挺だけ延ばす。**
- **#T3「落ちた時にCIを赤にするか」**: **推薦=赤にする**(緑を維持する意味が無くなるため)。
  ただし**偽陽性が続くなら、その項目だけ観察扱いへ落とす**(網を緩めるのではなく、項目を移す)。
