# SAME_ARENA.md — プレイヤー / 守護霊 / 幻影を「同じ土俵」に立たせる計画

## ゴール(社長の言葉のまま)
「**プレイヤー、守護霊、幻影 / 全て同じ土俵で戦わせたい。**
**サブウェポン、スキル、ステータス / これらを世界中のデータと戦わせたいのです。**」

関連する既存の裁定(事実として併記):
- 「**全てプレイヤーと同条件。じゃないと意味がないので。最終的にオンライン対戦を意識してください。**」(2026-08-19)
- 「**そもそも、守護霊も全部別財布にする必要がある**」「**開発後は特に指標がないなら全て独立させて、
  ちゃんとしたい。**」(2026-08-23・GHOST_PARITY_LEDGER.md ★裁定に記録済み)
- 「**敵なんだから共有するわけが無い。普通にAIとの対戦として考えれば分かること**」(2026-08-23)
  = 幻影の設置物・召喚・回復は**1対1の対戦としてそのまま鏡**にする。帰属に迷う余地は無い。

## 「ではない」条件(労力をかけない所)
- **リアルタイム対人戦ではない。** 戦うのは「記録されたビルド+癖」であって、生身の相手ではない。
  同期・遅延補償・マッチメイキングの類は対象外。
- **数値の精密バランスは対象外**(叩き台を出し、実機で社長が調整する)。
- **専用素材・UIの磨きは対象外**(既存の絵と枠を流用)。
- **サーバの新規開発は対象外**(既存の `src/online/` を流用する。増設が要ると分かった時点で別案件)。

### ここから直接出る結論
**「世界中のデータと戦わせる」の配管は、守護霊についてはもう出来ている。**
不足しているのは**配送**でも**保存**でもなく、**受け取った物を実際に使う側(消費層)**である。
よって本計画の本体は「オンラインを作ること」ではなく、**「主語を1本にして、3者が同じ関数を通ること」**。

## 2. 設計の背骨 — 「写すな、共通化しろ」を主語の統一で実現する

これまでの漏れ(守護霊にスキル倍率が乗らない・幻影が銃の基礎値しか使わない)は、すべて
**「プレイヤー用に書かれた計算を、他の主語ぶんもう一度書こうとして書き漏らした」**ことに由来する。
写経を続ける限り、**プレイヤーに何か足すたびに3箇所へ手で写す**必要があり、必ずどこかが漏れる。

**背骨**: `combatActorPlayer(actorId)` を**3者対応に一般化**し、戦闘系の関数はすべて
**主語を引数で受ける**(既定=プレイヤー)。これが済むと以後
**「プレイヤーに足した機能は、何もしなくても3者に乗る」**。

- **読み**: 疑似Playerを1枚組んで返す(ビルド+実体の座標/寸法/HP+その主語の状態)。
- **書き**: 宛先を主語で振り分ける専用の setter を通す。
- **幻影は Enemy シャーシ、守護霊は Summon シャーシ**のままでよい。
  「storeに2人目のプレイヤー実体を立てる」(GHOST_BOSS.md の北極星・**コスト8/10**)は**やらない**。
  疑似Playerで同じ効果が得られており、既に守護霊で実証されている。

## 3. 段取り(5段。段0以外は前段に依存する)

### 段0 — 現在地の確定(走査のみ・設計判断なし)
`GHOST_PARITY_LEDGER.md` §7 は**自己矛盾している**(表は katana/whip/wire-anchor/sensor-mine/shadow-clone を
「未対応」と書き、直下の総括行は「残る未対応は dog と CD概念なし系のみ」と書いている)。
ENGINEERING_NOTES「設計書のステータス行は腐る」の典型なので、**実コードで「今どの技が誰で動くか」の
表を作り直す**。これをやらないと以降の見積もりが全部空論になる。
- 成果物: サブ25種 × {プレイヤー / 守護霊 / 幻影} の実配線マトリクス(実コードの行番号つき)。
- 規模: **小**(走査のみ)。判断が要らないので実装サブエージェント向き。

### 段1 — 主語の統一(基盤・ここが本体)
1. `combatActorPlayer(actorId)` を **player / ghost-ally(Summon) / phantom(Enemy)** の3者対応へ一般化。
2. **別財布**(裁定済み): サブウェポンのCD帳簿を**主語ごとに独立**させ、`shouldGhostClaimSub` の
   予約方式を撤去する。「他者が使ったせいでプレイヤーが使えない」は**バグ扱い**へ格上げ。
3. 幻影(Enemy)を疑似Playerへ着せる口を作る(座標/寸法/HP/自前の状態)。
- **受け入れ条件**: 段2以降で「プレイヤー側の計算関数に主語引数を足す」だけで3者に効くこと。
  同じ計算を主語ぶん書き写した箇所が**1つも増えていない**こと。
- 規模: **中**。

### 段2 — ステータス(いちばん安く、いちばん効く)
skills / skillLevels / equipBonus / critChance / magBonus / reloadMult / growthAtkMult / speed を
**3者すべてに適用**する。
- **予告も帰属も要らない**(倍率が乗るだけ)。新しい絵もSEも要らない。
- 社長の元の不満「**めちゃくちゃ弱いなー**」に**一番速く効く**のはここ。
- 既知の障害: `isAllyOwnedShot`(`useGameLoop.ts:8220` 付近)が ghost の弾を escort と同枠にして
  **クリ倍率もスキル倍率も明示的にスキップしている**。「二重に乗らないよう安全側」というコメント付きだが、
  これは**2026-08-19裁定「全てプレイヤーと同条件」で否定された旧方針**なので撤去する。
- 規模: **中**(段1が済んでいれば小〜中)。

### 段3 — サブウェポン
- 幻影のサブは**紫の文法**(=カウンター不可)に流し込む。**24種ぶんの予告を新設しない。**
  色の文法(CLAUDE.md): 赤=カウンター可・判定と厳密一致 / **紫=カウンターできない攻撃**。
  プレイヤーが使う時もサブはカウンター対象ではないので、**紫で対称が保たれる**。
- 設置物・召喚・回復・分身は**1対1の対戦としてそのまま鏡**(裁定済み)。幻影のタレットはプレイヤーを撃つ。
- **★強glowを出すサブ(爆発系)は同時上限を持たせる。**唯一の実測有料項目(§5)。
- CD概念を持たない4種(whip / alchemy・sage-stone / shijin / striker-hunting)は
  **発動モデルが無い**ので、この段の**最後**に回す(種ごとにモデルを作る必要がある=ここだけ高い)。
- 規模: **中〜大**(CD概念のある種は中、無い4種が大)。

### 段4 — ロコモーション系(刀/村雨・ワイヤー・四神スライド・分身)
効果が「主語の体そのものの高速移動」なので、**プレイヤー本体の `movePlayer` に手が入る**。
`DashLocomotionState` の切り出し+`utils/dashLocomotion.ts`(純関数化)が要る。
- **この段だけ独立して落とせる。**落とすと段1〜3の規模は目に見えて下がる。
- **一番使われている武器(刀)のコードを触る**ので、リスクは本計画中で最大。
- 規模: **大**。

### 段5 — オンラインを幻影へ
守護霊が既に引いている remote record を、幻影も同じ経路で引く。**配管は流用**、新規サーバ開発なし。
- 規模: **小**(段1〜3が済んでいれば、主語を差し替えるだけ)。

### 推薦する順番
**段0 → 段1 → 段2 → 段3 → 段5**(**段4は最後に単独で判断**)。
段1を飛ばして段2をやると、また写経になる=これまでの漏れをもう一度作る。

## 4. デメリット — **開発だけではない。開発以外が4つある**

### D1. ゲーム全体の再バランスが必ず必要になる(最大・開発ではない)
3者がフルビルドで同じ土俵に立つと、**幻影は「世界の誰かの最強ビルド」**になりうる。
一方プレイヤーは**雑魚も捌きながら**戦う。**同条件は"公平"ではない。**
段2(ステータス)の直後に必ず表面化する。**これは実装で解決できず、社長の調整でしか収束しない。**

### D2. 「合法だが強すぎる」ビルドは素通りする(不正の残余)
`shared/ghostSanitize.mjs` は**ホワイトリスト+クランプまでは既にやっている**
(damageMult 0.1〜5 / critChance 0〜1 / skills ≤24・Lv≤3 / subWeapons ≤4 / 64KB上限)ので、
**でたらめな値の注入は既に防げている**。残るのは「**全項目が合法な上限**」のビルドで、
これは改造しなくても**やり込んだプレイヤーなら普通に到達する**。
⇒ 「倒せない幻影が配られる」可能性。**上限そのものの設計(強さの天井)が要る**=D1と同根。

### D3. 運用が続く(開発ではない・恒久)
「世界中のデータ」は**サーバが動き続ける**ことを意味する。配布方針は
「**Web公開はしない。最終形=アプリ配布(ストア)**」(v0.25.2549)なので、
**本体は売り切りでもサーバ代だけは毎月続く**。
加えて、他人の**名前・コメント**が流れる仕組みが既にある(`ghostComment` / `playerName`)以上、
**通報・遮断の責任**も持つことになる。※既存 `src/online/` の運用実態(どこで動いているか・費用)は
**本計画では未確認**。段5の着手前に確認が要る。

### D4. 将来の全機能への恒久税(開発だが、1回では終わらない)
主語を引数化すると、**以後プレイヤーに何か足すたびに「3者ぶん正しいか」を考える必要**が出る。
ただし段1をちゃんとやれば**「自動で乗る」側に倒せる**ので、実際の選択は
**「税を払う」か「毎回3箇所へ手で写して漏らし続ける」か**であり、前者が明確に安い。

### D5. 実行時コスト(**軽微・対策込み**)
- **唯一の有料項目=同時に出ている強glow**(`kind:'glow'` かつ `radius >= STRONG_GLOW_RADIUS`=44px)**の数**。
  実測 **1個 ≈ 2ms/フレーム(予算の約12%)**。爆発系サブを3者が同時に撃つと瞬間的に増える
  (寿命240〜900msなので持続はしない)。⇒ **段3で同時上限を持たせる**(明記済み)。
- 常駐召喚(錬金/タレット)が最大3セット。実測では敵36体(重量級)+弾70+粒子64 で 60fps 張り付きなので
  **効かないはず**だが、段3の実機で確認する。
- CD帳簿の別財布化そのものは**データ数百バイト・per-frame増分ゼロ**(判定の回数は変わらず、読む場所が変わるだけ)。

  何らかの上限・補正を掛けるのか。
  推薦: **まず素のまま段2を出し、実機で社長が体感してから天井を決める**(先に天井を設計すると、
  何を防いでいるのか分からないまま数字を置くことになる)。

  プレイヤー本体の `movePlayer` に触らずに済む。

  推薦: 流星式のまま windup 400ms(叩き台)。

  被弾無敵(毎秒1発)が入って戦闘時間が伸びているので、Q1と一緒に見るのが自然。

## 6. 受け入れ条件(この計画が「達成された」と言える状態)
1. プレイヤーに新しいスキル/装備/サブウェポンを足した時、**守護霊と幻影に何も書き足さなくても効く**。
2. **同じ計算式がコード上に2つ以上存在しない**(写経がゼロ)。
3. サブウェポンのCDで**3者が取り合わない**。
4. 幻影が**オンラインの他人のビルド**で戦い、そのビルドの skills/equipment/subWeapons が実際に効いている。
5. 強glowの同時数に上限があり、3者が同時に爆発系を撃っても**フレーム落ちしない**(実機確認)。
