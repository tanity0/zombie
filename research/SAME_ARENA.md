# SAME_ARENA.md — プレイヤー / 守護霊 / 幻影を「同じ土俵」に立たせる計画

## ゴール(社長の言葉のまま)
「**プレイヤー、守護霊、幻影 / 全て同じ土俵で戦わせたい。**
**サブウェポン、スキル、ステータス / これらを世界中のデータと戦わせたいのです。**」

関連する既存の裁定(事実として併記):
- 「**全てプレイヤーと同条件。じゃないと意味がないので。最終的にオンライン対戦を意識してください。**」(2026-08-19)
- 「**そもそも、守護霊も全部別財布にする必要がある**」「**開発後は特に指標がないなら全て独立させて、
  ちゃんとしたい。**」(2026-08-23・GHOST_PARITY_LEDGER.md ★裁定に記録済み)
- 「**敵なんだから共有するわけが無い。普通にAIとの対戦として考えれば分かること**」(2026-08-23)
  = 幻影の設置物・召喚・回復は**1対1の対戦としてそのまま鏡**にする。帰属に迷う余地は無い。

## 「ではない」条件(労力をかけない所)
- **リアルタイム対人戦ではない。** 戦うのは「記録されたビルド+癖」であって、生身の相手ではない。
  同期・遅延補償・マッチメイキングの類は対象外。
- **数値の精密バランスは対象外**(叩き台を出し、実機で社長が調整する)。
- **専用素材・UIの磨きは対象外**(既存の絵と枠を流用)。
- **サーバの新規開発は対象外**(既存の `src/online/` を流用する。増設が要ると分かった時点で別案件)。

## 2. 設計の背骨 — 「写すな、共通化しろ」を主語の統一で実現する

これまでの漏れ(守護霊にスキル倍率が乗らない・幻影が銃の基礎値しか使わない)は、すべて
**「プレイヤー用に書かれた計算を、他の主語ぶんもう一度書こうとして書き漏らした」**ことに由来する。
写経を続ける限り、**プレイヤーに何か足すたびに3箇所へ手で写す**必要があり、必ずどこかが漏れる。

**背骨**: `combatActorPlayer(actorId)` を**3者対応に一般化**し、戦闘系の関数はすべて
**主語を引数で受ける**(既定=プレイヤー)。これが済むと以後
**「プレイヤーに足した機能は、何もしなくても3者に乗る」**。

- **読み**: 疑似Playerを1枚組んで返す(ビルド+実体の座標/寸法/HP+その主語の状態)。
- **書き**: 宛先を主語で振り分ける専用の setter を通す。
- **幻影は Enemy シャーシ、守護霊は Summon シャーシ**のままでよい。
  「storeに2人目のプレイヤー実体を立てる」(GHOST_BOSS.md の北極星・**コスト8/10**)は**やらない**。
  疑似Playerで同じ効果が得られており、既に守護霊で実証されている。

### ★「望んでいる形」への最短路(2026-08-23・社長の問い「結局どうするのが一番望んでる形に仕上がるの?」への答え)

理由: **今の幻影が弱いのは3重で、うち2つは「未実装」ではなく意図的に落としてある**(走査で確認):

| 何が | 現状 | 出どころ |
|---|---|---|
| **ビルド(スキル/装備/サブ)** | **無し**。銃は**初期銃に固定** | `phantomTick.phantomGunKey()`。**社長裁定v0.25.3641「いまってスキルまだ無いんだよね? そしたら武器とかも初期で」**で、スキル未実装との釣り合いを取るため意図的に落とした。コメントに「**スキル再現が入る第3弾で戻す候補**」と明記 |
| **頭脳(癖)** | **固定台帳の最強データ**。実在の他人ではない | `phantomTick.phantomProfile()` = `strongestGuardian().profile` |
| **出現** | **デバッグ/練習の「決闘」枠だけ** | `FORCE_PHANTOM` / `practiceForces('phantomnow')` |

⇒ **「世界中のデータと戦う」に効くのは、サブウェポン(O-3)ではなく ①ビルドを乗せる(O-1+O-2)
②中身を他人にする(O-5)③本番に出す(Q6)の3つ。**
O-3/O-4 は「**何を持って戦うか**」を厚くするが、「**誰と戦っているか**」を変えない。

**★O-2 の着地で v0.25.3641 の前提が消える**(「スキルが無いから武器も初期で」の理由が無くなる)。
コード側も「第3弾で戻す候補」と書いてあるので、**O-2 と同時に戻すかを社長に確認する(★Q7)**。

**★O-5 では「ビルド」だけでなく「癖(プロファイル)」も他人のものにする。**
`phantomProfile()` が固定台帳を返している限り、装備が他人でも**戦い方は同じ1体**のまま。
「誰と戦っているか」を作るのは、実は癖の側の比重が大きい。

**推薦する順**: **O-1 → O-2 → O-5 → O-3 → O-4 → O-6 → O-7**
理由: **O-2 までで「めちゃくちゃ弱いなー」が直る**(スキル・装備が乗る)。

O-6 は独立しているので、いつでも割り込める。

**やらないこと**: 「storeに2人目のプレイヤー実体を立てる」(GHOST_BOSS.md の北極星・**コスト8/10**)。
疑似Playerで同じ効果が得られており、**守護霊で完全に実証済み**(§1)。

## 3-b. O-1 の詳細(発注できる粒度・2026-08-23 実コードで確認)

### なぜ安いのか
**`ghostActorPlayer(build, actor)`(`utils/ghostBuild.ts:79`)の第2引数は構造型**
`{x, y, width, height, health, maxHealth}` **であって Summon 型ではない**。
`Enemy` はこの形をそのまま満たすので、**幻影を渡すだけで通る=新しい式を1本も書かない**。
`resolveGhostBuild(snap, live)` も純関数なので同じく流用できる。

### ★O-1 で必ず直す実バグ予備軍(走査で発見)
`ghostBuildFor`(`utils/ghostBuild.ts:64`)のメモ化は **`cached = { id, build }` の1件だけ**。
現状は守護霊が同時1体なので露見していないが、**守護霊と幻影が同時に居ると id が交互に変わり、
毎フレーム `resolveGhostBuild`(武器生成を含む)を作り直す**。
コメント自身が「ここで実体側の帳簿を重ねないとCD表が召喚時点で凍る(v0.25.2525の実バグと同型)」と
警告している系統そのもの。**O-1でキャッシュを id をキーにした Map へ広げる**(上限は同時実在数=数件)。

1. `combatActorPlayer(<幻影のid>)` が、**幻影の座標・寸法・HP** と **`phantomBuild` 由来のスキル/装備/クリ率/サブウェポン**を載せた1枚の `Player` を返す。

## 4. デメリット — **開発だけではない。開発以外が4つある**

### D1. ゲーム全体の再バランスが必ず必要になる(最大・開発ではない)
3者がフルビルドで同じ土俵に立つと、**幻影は「世界の誰かの最強ビルド」**になりうる。
一方プレイヤーは**雑魚も捌きながら**戦う。**同条件は"公平"ではない。**
段2(ステータス)の直後に必ず表面化する。**これは実装で解決できず、社長の調整でしか収束しない。**

### D2. 「合法だが強すぎる」ビルドは素通りする(不正の残余)
`shared/ghostSanitize.mjs` は**ホワイトリスト+クランプまでは既にやっている**
(damageMult 0.1〜5 / critChance 0〜1 / skills ≤24・Lv≤3 / subWeapons ≤4 / 64KB上限)ので、
**でたらめな値の注入は既に防げている**。残るのは「**全項目が合法な上限**」のビルドで、
これは改造しなくても**やり込んだプレイヤーなら普通に到達する**。
⇒ 「倒せない幻影が配られる」可能性。**上限そのものの設計(強さの天井)が要る**=D1と同根。

### D3. 運用が続く(開発ではない・恒久)
「世界中のデータ」は**サーバが動き続ける**ことを意味する。配布方針は
「**Web公開はしない。最終形=アプリ配布(ストア)**」(v0.25.2549)なので、
**本体は売り切りでもサーバ代だけは毎月続く**。
加えて、他人の**名前・コメント**が流れる仕組みが既にある(`ghostComment` / `playerName`)以上、
**通報・遮断の責任**も持つことになる。※既存 `src/online/` の運用実態(どこで動いているか・費用)は
**本計画では未確認**。段5の着手前に確認が要る。

## 3-g. ★設置物の「宛先」配線(2026-08-24〜25・O-3b-2の本体)

§3-f で**壊せるようになった**ので、幻影へ解禁した設置物が**実際に働く**ようにする段。
やることは §3-f 末尾の3つのうち③「宛先をプレイヤーへ」。

### 共通の作法(5種すべて同じ)
**数字を2組に分けない。** 半径・間隔・射程・信管・減衰・壁越し判定の式は**共通のまま**にして、
**「誰を見るか」と「撃った物の側」だけ**を `hostile` で分岐する。
理由: 味方側だけ調整された時に敵対側が置き去りになる事故を、構造として作らない。
プレイヤーへ与えるダメージには `PVP_DAMAGE_SCALE`(0.2)を掛ける。

| 設置物 | 宛先の分岐 | 版 | 状態 |
|---|---|---|---|
| **デコイ** | 撃ち落とす弾を `(弾の側 === デコイの側) なら見送る` の1本に | v0.25.3884 | 完了 |
| **自動タレット** | 索敵を `tHostile ? プレイヤー : 敵`。弾は `hostile: tHostile`。消滅爆発も同じ式で宛先だけ差替 | v0.25.3885 | 完了 |
| **センサー地雷** | 感知対象を `const watch = m.hostile ? player : enemies` の1行に | v0.25.3885 | 完了 |
| **盾** | ★**分岐を作らない**(下記裁定) | v0.25.3885 | 完了 |
| **トラップ** | ★**拘束をやめて4効果**(下記の裁定) | v0.25.3886 | 完了 |

### ★裁定: 幻影の盾はバッシュで押せない(社長2026-08-25・推薦採用)
`shieldShoves` から `hostile === true` を除外する。押せてしまうと
**「敵の盾を奪って自分の武器にする」**ことになり、耐久を設定した意味が薄れる。
敵対の盾は**近接で削って壊すだけ**(すり抜けない=接触判定は元から側に関係なく効いている)。

### ★裁定: 対人トラップは「拘束」ではなく4つの効果(社長2026-08-25)
**社長の言葉のまま**: 「トラップ効果中は / 移動が等倍のみ(かさまし%ダッシュが無効) /
クリティカル率アップ / リロード時間1.5倍 / CD短縮系も無効 / で / 対人のみね」

**私の推薦(大幅な鈍足)は採らなかった**——社長案の方が良い。鈍足は「遅くなる」1軸だけだが、
この4つは**逃げ・撃ち返し・道具の回転を同時に鈍らせて、殴り合いの土俵へ引きずり出す**。
拘束のように「何もできない時間」は作らないので★未決9の再現も避けている。

| # | 効果 | 実装の場所(1箇所ずつ) | 効き方 |
|---|---|---|---|
| ① | 移動が等倍のみ | `gameStore.movePlayer` | **`Math.min(移動速度, player.speed)` の1本**。かさまし%(ランナー/マークスマン/消費カード/装備)・スケーター×3・ダッシュ系(一閃/ワイヤー/ホップ)・四神スライド・**踏み込み**が、個別の分岐を書かずにまとめて頭打ちになる。リロード中の減速など**素より遅い**ものは min なので残る |
| ② | クリティカル率アップ | `phantomTick.phantomAtkMults` | **貰う側が貰いやすくなる**向き。量は対敵の `TRAP_ROOT_CRIT_BONUS`(拘束中の敵は+10%)と**同じ+10%**=数字を2組に持たない |
| ③ | リロード時間1.5倍 | `weaponUtils.effectiveReloadMs` | 唯一の式に乗算。**下限250msの床は残す**(掛けてから max) |
| ④ | CD短縮系も無効 | `subCooldown.applySubCooldownSkills` の呼び出し3箇所 | オーバークロックの抽選確率→0 / タイムキーパー倍率→1 |

- **効果時間=3秒**(`TRAP_PVP_DEBUFF_MS`)。敵側の拘束 `MARKSMAN_TRAP_STUN_MS` と**同じ長さ**。
- **「対人のみ」はフィールドの有無で自然に成立する**: 判定は `player.trapDebuffUntil` の1本で、
  幻影・守護霊の疑似Playerはこのフィールドを持たない=同じ関数を通しても素通しになる。
  (**条件分岐で「幻影なら」と書かない**。書くと写し忘れが必ず出る。)
- 時計は **Date.now**(プレイヤー側の他のタイマーと同じ系)。敵の `rootUntil` だけが gameTime 系。

#### ★この裁定で残る2つの穴(握り潰さずここに書く)
1. **②が効くのは幻影の「銃」だけ**。幻影の**近接にはそもそもクリ抽選が無い**
   (`phantomMeleeDamage` の「クリは未適用(叩き台)」=既存仕様)。近接にもクリを入れるのは
   **仕様変更**なので勝手にやらない。**社長裁定が要る**。
2. **逆向き(プレイヤーのトラップ→幻影)は今も「拘束」のまま**。幻影は `enemies` の一員なので
   従来の `rootEnemy` を踏む。**同じ土俵の原則からは揃えるべき**だが、揃えると
   **プレイヤーのトラップが幻影に対してだけ弱くなる**(拘束→4効果)ので、これも**社長裁定が要る**。

## 3-f. ★設置物の耐久(社長指示2026-08-24)— O-3b-2 の前提条件

社長: 「デコイやトラップ、自動タレットなどは近接一撃で壊せる様にして。地雷とか設置系全て」
→ 「**それぞれに耐久値設定して**」/ 対象は「**もちろん幻影の**」

### 決まったこと
- **壊せるのは敵対側(幻影)が置いた物だけ**。判定は `hostile === true` の1本
  =**自分の設置物は絶対に壊れない**(誤爆で自分のタレットを失う事故を作らない)。
- **耐久台帳は `gameStore.PLACED_DURABILITY` の1箇所**。近接の素ダメージ(ナイフ22)を目安に:

| 設置物 | 耐久 | 目安 | なぜ |
|---|---|---|---|
| トラップ / 地雷 | **20** | 1撃 | 仕掛け物は脆い。**踏まずに処理できる**のが遊びの主眼 |
| デコイ | **45** | 2撃 | 囮なので少しだけ粘る |
| タレット | **70** | 3撃 | 居座って撃ち続ける=盤面でいちばん硬い |
| 盾 | (対象外) | — | `SHIELD_HP_BY_LEVEL`(10/30/60)+接触ダメージという**独自の体系**を既に持つ |

- 近接スイングの合流点から `damageHostilePlacements()` を1回呼ぶ
  =**刀/鞭/ナイフのどれで振っても同じ1本**を通る。地雷は器が別(`sensorMines`)だが
  **同じ関数の中で両方を見る**ので、呼ぶ側は器を知らなくてよい。

### ★これは O-3b-2 の前提条件
現時点では**幻影は設置系を置けない**(§3-e の白リスト)ので、この破壊経路は**まだ発火しない**。
逆に言えば、**「プレイヤーが壊せること」が揃ったので、O-3b-2 で設置系を幻影へ解禁できる**。
解禁時にやることは①白リストへ追加 ②置いた物へ `hostile: true` ③宛先をプレイヤーへ、の3つ。

## 3-e. ★実機バグ「幻影の自爆」と、その構造的な予防(2026-08-24)

**社長報告(実機)**: 「幻影が自分のデコイに消されてたり、自分のトラップにハマってる」

### 真因は「所有者判定の漏れ」ではなく「未実装の種を使わせていた」
サブの主語ディスパッチ(`useGameLoop.subSubject`)は
**「その種を持っていて自前CDが明けていれば幻影が主語」**という**汎用の式**なので、
**O-3b-2 でまだ実装していない種まで幻影が使えていた**。

設置系(トラップ/デコイ/タレット/盾/地雷)は例外なく
**「`enemies` を走査して敵を捕まえる」**形で書かれている。幻影は `enemies` の一員なので:
- **宛先にプレイヤーが入らない**(プレイヤーは `enemies` に居ない)=そもそも機能しない
- **自分自身が唯一の候補になる**=自分のトラップで拘束され、自分のデコイに処理される(=自爆)

つまり §3-d「残りのサブは同型の繰り返しではない」が指していた事実が、**実機で先に出た**。

### 予防: 白リストを「実装した」の定義にする
`phantomTick.PHANTOM_SUPPORTED_SUBS` に**実装済みの種だけ**を列挙し、`subSubject` が通す。
未実装はプレイヤーへフォールバック(=従来どおり動く)。
**O-3b-2 で1種実装したら、その時ここへ足す**——白リストを増やすことが「実装した」の意味になるので、
**足し忘れ=自爆の再発が構造的に起きない**。テスト(`phantomSubs.test.ts`)で値を固定した。

## 3-d. O-3b: 残りのサブは「同型の繰り返し」ではない(2026-08-23・走査で判明)

O-3a の想定は「土台が済めば残りは同じ型の繰り返し」だったが、**投擲系だけが同型**だった。
残りは**効果の届け方そのものが違う**ので、種類ごとに別の手当てが要る。

| 群 | 種 | 何が要るか | 規模 |
|---|---|---|---|
| **投擲系** | heavy-grenade / fire-knife | **同型**(狙いをプレイヤーへ+hostile+noCounter+紫) | ✅済 |
| **設置系** | turret / marksman-trap / shield / decoy | **設置物の"敵"の定義を反転**する必要がある。例: タレットの索敵は `enemies` を直接舐めており(全方位=最近接/前方=射線帯スキャン+`turretAimRef` の向き記憶)、**幻影のタレットがプレイヤーを撃つ**には索敵対象を主語で切り替える配線が要る | **中〜大** |
| **床** | molotov | 火のDoTが敵を焼く。幻影の火は**プレイヤーを焼く**必要がある | 中 |
| **自分に効く系** | first-aid-kit / striker-quick-mag / support-sniper | 受け手が自分なので**ほぼそのまま**動くはず(要確認) | 小 |
| **近接スイング相乗り** | drone-boomerang / flare-gun / junk-weapon | 発動入口が**プレイヤーの近接スイング**。幻影の近接は別経路(`swingPhantomMelee`)なので**入口の配線**が要る | 中 |
| **ロック系** | homing | ロックの対象が敵。幻影は**プレイヤーをロック**する | 中 |
| **★召喚系** | alchemy / shadow-clone / dog / support-sniper | **この表に入っていなかった**(2026-08-25 社長の問い「召喚はどうなってる?」で発覚)。下の §3-d-2 に分けて書く | **要裁定** |

### §3-d-2 ★召喚系の現在地(2026-08-25・社長の問いで起票)

**答え: 幻影は召喚系を1種も使えない**(`PHANTOM_SUPPORTED_SUBS` に1つも入っていない)。

| 種 | プレイヤー | 守護霊 | 幻影 | 幻影で止まっている理由 |
|---|---|---|---|---|
| **分身** shadow-clone | ✅ | ✅ 主語ごとの枠(v0.25.2541) | ✗ | `shadowCloneStrike` が `enemies` を舐める |
| **錬金術** alchemy | ✅ | ✗ **発動モデルが無い**(立ち止まり5秒チャネル=CD概念を持たない・O-6) | ✗ | 召喚先が `summons`=**プレイヤーの味方配列** |
| **ドッグ** dog | ✅ | ✗ ★未決6(霊体は世界の物に触れない) | ✗ | 拾い物を**プレイヤーへ**運ぶ |
| **援護射撃** support-sniper | ✅ | (自分に効く系として未確認) | ✗ | 撃つ相手が `enemies` |

#### ★ここが設置系より危ない: 有効にすると「自爆」より悪い
設置系の自爆(§3-e)は**幻影が自分を害する**だけだったが、召喚系は**幻影がプレイヤーを利する**。
4種とも狙い/届け先が `enemies` か `summons`(=プレイヤーの味方配列)なので、
白リストへ足しただけで**幻影がプレイヤーの味方を呼ぶ**。**白リストが正しく止めている。**

#### ★設計の抜け道: 幻影の召喚に `summons` は要らない
味方召喚の仕組みを鏡写しにする必要はない。**敵側には既に「敵を出す」仕組みがある**ので、
**幻影の召喚=`enemies` へ1体スポーンするだけ**でよい(AI・当たり判定・描画は既存のまま)。
設置系のように「宛先を反転する」配線が要らないぶん、**設置系より安い可能性が高い**。

#### 裁定が要る点(実装では決められない)
1. **何を召喚するか。** 分身=幻影のコピー(=もう1体の幻影)か、雑魚か。
2. **錬金術の発動モデル。** 立ち止まり5秒チャネルは幻影の頭脳に「立ち止まる」概念が要る
   (守護霊が O-6 で止まっているのと同じ壁)。
3. **ドッグ・援護射撃をやるか。** どちらも「プレイヤーへ運ぶ/味方を撃つ」が本体なので、
   敵側での意味を作り直すことになる=**別の技を作るのに近い**。

**推薦(今ベストだと思う案)**: **分身1種だけを先にやる**。幻影のコピーを1体出すのは
①絵が既にある(幻影そのもの)②`enemies` へスポーンするだけ ③「もう1人増える」は対戦として読める、
の3点で最も安く、いちばん効く。錬金術・ドッグ・援護射撃は O-6(守護霊の残り穴)と同時に扱う。

### ★decoy は設計判断が要る(★未決Q9)
デコイは**敵を引きつける**サブ。幻影が置いても引きつける相手は雑魚=**プレイヤーを助けてしまう**。
「幻影のデコイ」が何をする物なのかは実装では決められない。
推薦: **O-3b-2 では decoy を対象外にする**(dog が★未決6で止まっているのと同じ扱い)。

## 4-d. ★★裁定(社長2026-08-23)— **幻影は「侵入者」。世界の敵は幻影を襲わない**

社長の問い「**幻影や守護霊にも敵が向く様にできるかなー**」→「**エルデンリングってどうしてる?**」→ **「1で」**。

### エルデンリングの答え(2つを別々に扱っている)
| 向こうの概念 | このゲームの対応 | 世界の敵の扱い |
|---|---|---|
| **遺灰・協力の霊** | **守護霊(ghost-ally)** | **敵もボスも普通に狙う**。囮・壁として機能するのが前提(遺灰の存在意義そのもの)。協力人数でボスHPが上がる=**このゲームの `ghostHpBoosted`(城ボス×1.6)と同じ考え方**が既に入っている |
| **侵入者・赤い霊** | **幻影(guardian-phantom)** | **世界の敵は侵入者を襲わない。** 侵入者は敵側の陣営 |

**侵入者を襲わない理由(設計として)**: 侵入者が世界の敵に襲われたら1対多で即死する。
**ホスト側の有利は「世界が味方であること」**で、**侵入者側の有利は「奇襲」**で表現し、
**同士討ちの仕組みを作らずにバランスを取っている。**

### 確定
- **幻影の同士討ち(敵が幻影を襲う/幻影が雑魚と戦う)は作らない。** 現在の実装が既にこの形。
  - 実装上も裏付けがある: `checkProjectileEnemyCollisions` は **`if (projectile.hostile) return;`**
    =**敵の弾は敵に当たらない**。敵↔敵の接触ダメージ経路も無い。**新概念を足さずに済む。**
  - **⇒ 「大」と見積もっていた作業がまるごと不要になった。**
- **今後「幻影が周りの雑魚と戦わないのは不自然では?」と再提起しない。**
  不自然に見えるのは**侵入者という枠組みを知らない場合**で、枠組みとしては正しい
  (エルデンリングが同じ問題に対して選んだ答えと一致)。

### この裁定に含まれないもの(別件)
- **守護霊を雑魚にも狙わせるか**は**未決のまま**。現状は「ボスは狙う/雑魚は殴られた後のヘイト時だけ」
  (v0.25.2490 で**意図的に既定候補から外した**)。エルデンリングに寄せるなら雑魚も狙う側だが、
  **外した理由(囮が強すぎた等の実測)を先に確認してから**判断する。
- **giantbat / idol / 天使6体**が守護霊を狙わない件(標的をプレイヤーに直書きで共通経路を通らない)は
  **既知の★未決のまま**(`enemyUtils.resolveEnemyTarget` のコメントに記載済み)。

## 4-c. ★★原則(社長方針2026-08-23)— **記録が持つのは「持ち物」。数値は今の表から引く**

社長の言葉: 「**持つべき情報はビルドであって、何を持ってるのか? さえ分かれば、あとはゲーム内の
規定数値(HPに限らず全数値)に変換すればいいだけであれば / 後から数値仕様が変わっても、勝手に揃うはず**」

- **確定**: 記録(スナップショット)から**引ける数値は、記録の値を信じず"今の表"から引く**。
  記録に焼かれた数値は**識別子が欠けた旧データのフォールバック**としてだけ使う。
- **実装の1点**: `utils/playerBuild.buildPseudoPlayer` が唯一の変換点。ここを直せば
  **守護霊と幻影の両方**が同時に従う(消費側は他に無い)。

| 項目 | 扱い | 理由 |
|---|---|---|
| **最大HP** | **引く**(`PLAYER_PROFILES[class].maxHp + equipMaxHealthOf(equipment)`) | クラスと装備が判れば決まる |
| **装備効果(equipBonus)** | **引く**(`aggregateEquipBonus(equipment)`) | 100%装備から決まる。**改造耐性にもなる**(盛った equipBonus を送られても効かない) |
| speed | 記録のまま | 現状はラン開始値の定数(87)そのもの |
| **クリ率 / 装填加算 / リロード倍率** | **記録のまま** | **レベルアップで積んだ本人の選択**=持ち物から引けない。これ自体がビルドの一部 |
| level | 記録のまま | そのランの事実 |
| 育成倍率(growthAtkMult) | 記録のまま | 別軸。社長裁定2026-08-23で**保留中** |

### ★この原則が無いと何が起きたか(実例・社長が発見)
固定守護霊の記録は `maxHealth = 120 + 装備` で焼かれていたが、**プレイヤーの実際の初期HPは 130**
(`PLAYER_PROFILES[class].maxHp`。実際の式は `maxHealth = profile.maxHp + 装備 + 育成`)。
`gameStore.PLAYER_BASE_HP` に **120 という使われていない定数が残っていた**ため、
記録・コメント・テストの3つが**120側で辻褄が合ってしまい、10ズレたまま誰も気づかなかった**。
社長の指摘(「みんな130を初期値としてるよね?」)で発覚。
**引く形にすれば、この種のズレは構造的に起きない。**

### 掟(今後)
- **記録に数値を足したくなったら、まず「持ち物から引けないか」を考える。** 引けるなら足さない。
- **テストにも数値を写経しない**(`expect(...).toBe(1.2)` ではなく `aggregateEquipBonus(gear).damageMult` と書く)。
  写経したテストは、表を変えた時に**「一致している」と嘘をつく**(上の実例がまさにそれ)。

## 7. ★★裁定(社長2026-08-24)— 近接に前隙200ms。打ち合いは「後から振った方の勝ち」

### 社長の決定(そのまま)
- 「近接前隙を**200**にして、あとは実装して」
- 「**カウンターされた側はノックバックも敵と同じく**」

### 決定に至った事実(議論の要点だけ・経緯は残さない)
1. しゃがみの絵は**既に存在**する(`MELEE_POSE_READY_FRAC=0.4` → 280ms×0.4=**112ms**)が、
   **ダメージは指を離した瞬間(t=0)に確定**していた。**絵だけが嘘をついていた**状態。
2. このゲーム自身が**人の反応=250ms**(`bossSkeleton.HUMAN_REACTION_MS`)を持ち、
   **カウンター可能な予告の下限=550ms**(`MIN_COUNTER_TELEGRAPH_MS`)を機械検査している。
   ⇒ **前隙200msは「反応して返す」ことが原理的にできない長さ**。これは承知の上での決定
   (=近接の打ち合いは**反応ではなく予測**の読み合いになる)。
3. 三択のうち2つしか取れない: ①短い前隙 ②後出しが勝つ ③反応で決まる。
   **社長は①+②を採り、③を捨てた。**

### 確定仕様(発注文)

#### S-1. 近接に前隙 200ms
- `MELEE_WINDUP_MS = 200`(**唯一の出どころ**。絵の割合もここから導く=二度とズレない)。
- **指を離した瞬間(t=0)にやること**: カウンター窓を開く / 近接CDを張る / スイング絵の起点を打つ /
  刀ダッシュ・ワイヤーのフリック判定(**従来どおり**)。
- **t=200 でやること**: 近接の当たり判定・ダメージ・キル・フィニッシュ・コンボ・近接SE・
  スイング入口のサブウェポン(ブーメラン/地雷/フレアガン/ジャンク)。
- **絵の同期**: しゃがみが200ms続くよう、スイング全体を `MELEE_WINDUP_MS / MELEE_POSE_READY_FRAC`
  から導く(振り抜きの長さは現状維持)。

#### S-2. 打ち合い=「後から振った方のカウンターが成立」(新システムを作らない)
既存の2つだけで成立する: **①指を離すと窓が即開く ②窓の中の攻撃はカウンターになる**。
```
A が t=0 に振る   → A の窓 0〜400 / A の斬撃 t=200
B が t=100 に振る → B の窓 100〜500 / B の斬撃 t=300
t=200: A の斬撃が B の窓の中 → B のカウンター成立 + A は振りが中断
```
- **カウンターされた側は、前隙中の振りが中断される**(`pendingSwing` を破棄)。
- **★カウンターされた側はノックバックを受ける(社長指示)。敵がカウンターされた時と同じ量**
  (`KNOCKBACK_SPEED` / `KNOCKBACK_DURATION`)。**プレイヤーが受ける側でも同じ**。
- 完全同時(数フレーム内)は互いの窓に入るので**相互カウンター=相殺**。稀なケースとして許容。

#### S-3. カウンター成立からの反撃は前隙ゼロ
雑魚戦の連鎖(=腕前でサクサク刈る)を守るため、**カウンター成立を起点に出る近接は即発**。
「守りは即応 / 攻めは約束 / 読み勝ちは即座に返せる」の3層。

#### S-4. 幻影・守護霊も同条件
- **同じ `MELEE_WINDUP_MS` を持つ**(振ってから200ms後に判定)。
- **★訂正(v0.25.3869・実装で判明)**: 当初「幻影の近接パリィ窓は撤去」と書いたが、**逆だった**。
  あの窓(`gpSwingAt + COUNTER_WINDOW`)は**プレイヤーの `counterWindowEnd` の完全な鏡**であり、
  前隙が入った今こそ**正しく機能する**——幻影が後から振れば、その窓がプレイヤーの
  200ms遅れの斬撃を捕まえる=「後出しが勝つ」そのもの。**残す。**
  前隙ゼロの時代は「振った瞬間に当たる攻撃」を窓で弾いていたので理不尽に見えていただけだった。
  **足りないのは逆側**——プレイヤーが幻影の近接をカウンターする経路が存在しない。そちらを新設する。
- **幻影の反応に人間の下限を入れる**: `reactionMs` を `HUMAN_REACTION_MS`(250)で下限クランプ。
  台帳の100〜130msのままだと**幻影だけが前隙200msに反応で後出しできる**=最悪の不公平になる。

### §7-2 ★裁定(社長2026-08-24)— 刀の一閃は「着地後の判定」/ スラッシャーは200のまま

**刀の一閃**: 「一閃は推薦のとおりで」= **標的の選定を着地時へ移す**。
- 旧: 発動の瞬間に**予定**経路(始点→始点+`KATANA_DASH_DISTANCE`)で標的を確定していた。
  ⇒ ①壁で止まっても予定どおり斬れる ②移動の180ms分 敵が動いても反映されない(=かわせない)。
- 新: 始点と向きだけを焼き、**着地した実位置まで**(=実際に通った経路)で取り直す。
  ⇒ **新しい数字を足さずに `KATANA_DASH_MS`(180ms)がそのまま前隙**になる。空振り=かわされた。
- ※ダメージ**適用**が着地後なのは従来どおり(ヒットストップが移動窓を食う対策)。動いたのは**選定**。

**スラッシャーの追撃**: 「そのまま通して。200で。**CD短縮されてるのが褒美なので**」
= 前隙は他と同じ200msのまま(専用の短縮はしない)。報酬は `SLASHER_CHAIN_CD_MS`(300ms)という
**チェーン専用の短いCD**が既に担っている。**コード変更なし**(現状が裁定どおり)。

**刀の自動斬撃**: 「弾と同じ扱いで」= `KATANA_SLASH_INTERVAL_MS`(600ms)のタイマー駆動で、
入力の振りではない。**前隙は付けない**(現状どおり)。

### §7-3 ★裁定(社長2026-08-24)— 前隙は全武器200ms / 鞭に「しなり(スネア)」

- **鞭の前隙は200ms**(一度250msにしたが「200でいこ」で撤回)。鞭は `WHIP_DAMAGE_MULT`=0.25 の
  低ダメージ役なので、出まで遅くすると重くなり過ぎる。**測る側は必ず `meleeWindupMs()` を通す**
  ——武器別にしたくなった時、1箇所の分岐で判定も絵も同時に追従させるため。
- **鞭に しなり(スネア)を入れる**(社長指示「馬乗りには入ってるのにプレイヤーに入れてなかった。
  かなり強めに折れるくらいに入れたい」)。素材 `fx/whip-smear-0/1/2` は
  **①小さく巻く → ②S字にしなる → ③伸び切って打つ**の3コマで、**前隙にそのまま対応する**:
  前隙の前半=① / 後半=② / 判定が出てから=③。**振り始め(`beginMeleeSwing`)で出す**のが肝。
  判定を持たない分類②の絵なので、しなりは判定より**大きく**出す(`WHIP_SNARE_BEND_SCALE`=1.45)。

### §7-4 ★裁定(社長2026-08-24)— 近接に「踏み込み」を付ける(無敵なし)

**社長の思惑(言葉のまま)**: 「前隙が生まれたことで、踏み込み(近接2段目のような)の重要性が増した気がする」
「**踏み込む(しゃがみ)を早めに着地させれば、自ずと回避にも使える様になる**」「無敵はつけない。すでにカウンターがあるので」

- **前隙の頭で `lastDirection` へ滑る**。`MELEE_LUNGE_PX`=**30**(社長調整2026-08-25で50→30) / `MELEE_LUNGE_MS`=90。初速最大→線形に0。
- 前隙200msの内訳が **0〜90ms=踏み込み → 90〜200ms=足を着いて振りかぶる → 200ms=斬る**
  =**物理的に正しい順序**になる。
- **回避として成立する速度**: 平均333px/s=素の足(87px/s)の約3.8倍(50px当時は555px/s=6.4倍)。
  刀の一閃(154px/180ms=856px/s)より遅く短いので**一閃の格は保たれる**。
- **無敵は付けない**。「速く動いて避ける」であって「判定をすり抜ける」ではない
  =今日作った同条件の土俵(近接/カウンターは無敵を貫通する)を壊さない。
- **向きは常に `lastDirection`**(=振る向きと同じ)。前進中は前へ・後退中は後ろへ。
  **★当初私は「敵がいる時だけ詰める」を推薦したが、社長指摘「前に出るのか出ないのか分からない方が
  使いづらい」で取り下げた**——入力に対する結果が一定であることの方が、状況に応じた賢さより重い。
- **プレイヤー・守護霊・幻影の3者に同じ値**で入れる(同条件原則)。
- **★武器別(社長指示2026-08-24「鞭は踏み込み20で」)**: 鞭は `WHIP_LUNGE_PX`=**20px**。
  鞭はリーチ150px(素の近接74pxの倍)なので**そもそも踏み込む必要が薄く**、50px入ると
  「長物なのに毎回懐へ入る」ちぐはぐな動きになる。武器別の値は `meleeLungePx()` に集約する
  (前隙の `meleeWindupMs()` と同じ作法=測る側3箇所が必ずこの関数を通る)。
- **実装の掟**: 座標を自前で書かず、**既存のノックバックの器**(プレイヤー=movePlayer / 幻影=updateEnemies /
  守護霊=移動クランプの直前)へ載せる。壁と「行ける帯」のクランプを丸ごと共有するため
  (踏み込みは**いちばん帯の穴を踏みやすい機能**。v0.25.3875 の事故と同型を作らない)。

### §7-5 ★踏み込み中に何が当たるのか(社長の問い2026-08-25への答え・実配線で確認)
**社長の指摘が正しく、私の以前の説明(「弾・技・予告は当たる」)は不正確だった。**
正しくは **「カウンター不可(紫)のものだけが当たる」**。理由は時間の重なり方:

- カウンター窓は**指を離した瞬間**に開き、`COUNTER_WINDOW`=**400ms** 続く。
- 前隙は200ms、踏み込みはその頭の90ms。**どちらも丸ごと窓の中**に入っている。

したがって踏み込み中に飛んできたものは:

| 来るもの | どうなるか | 実配線 |
|---|---|---|
| 敵弾(既定) | **反射**(`REFLECT_DAMAGE_MULTIPLIER`=10倍で返る) | `combatTick.applyEnemyProjectileHits` が `counterWindowEnd` を見る |
| 敵弾(紫=`noCounter`) | **当たる** | 同上の `!proj.noCounter` 条件 |
| 技・予告(赤い帯/線) | **Counter! で弾く** | 各技の判定側が `cp.counterWindowEnd` を見る(トールの一閃/突き/払い等) |
| 必中(無の境地の一閃) | **当たる** | `issenGuaranteedUntil` が立っている間だけ窓を見ない |
| 敵の接触ダメージ | **当たらない** | 踏み込み中だけ無効(社長裁定v3882) |

**つまり「無敵は付けない」は、実効としては「紫にだけ無防備」という意味**になる。
これは弱体ではなく**カウンターの土俵がそのまま効いている**だけで、意図どおり。
(この表が要るのは、**「無敵なし」という言葉だけを読むと踏み込みが危険に見える**ため。)

### 受け入れ条件
1. `MELEE_WINDUP_MS` が唯一の出どころで、絵の尺がそこから導かれている(テストで固定)。
2. 指を離した瞬間にカウンター窓が開く(**従来と同時刻**)。判定だけが200ms後。
3. 前隙中にカウンターされたら振りが出ない+ノックバックを受ける(**敵と同じ量**)。
4. カウンター成立からの反撃には前隙が乗らない。
5. 幻影・守護霊の近接も200ms前隙。幻影の**近接**パリィは消え、**弾**パリィは残る。
6. 幻影の `reactionMs` が 250 未満にならない。
7. 通常の敵・環境ダメージの挙動は1bitも変わらない。

### ★実装の方針(800行の `triggerCounter` を割らない)
判定の中身を分割するのではなく、**関数の呼び出しごと200ms遅らせる**:
- `beginMeleeSwing()`(新設・小さい): 窓/CD/絵の起点/`pendingSwingAt` を打つだけ。
- `useGameLoop` が毎フレーム `pendingSwingAt` を見て、200ms経過で**既存の `triggerCounter` を呼ぶ**
  (窓/CDの二重張りだけ抑止するフラグを1つ渡す)。
- こうすると **800行の中身に一切手を入れずに**前隙が入る=回帰面が最小になる。
