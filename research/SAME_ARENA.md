# SAME_ARENA.md — プレイヤー / 守護霊 / 幻影を「同じ土俵」に立たせる計画

## ゴール(社長の言葉のまま)
「**プレイヤー、守護霊、幻影 / 全て同じ土俵で戦わせたい。**
**サブウェポン、スキル、ステータス / これらを世界中のデータと戦わせたいのです。**」

関連する既存の裁定(事実として併記):
- 「**全てプレイヤーと同条件。じゃないと意味がないので。最終的にオンライン対戦を意識してください。**」(2026-08-19)
- 「**そもそも、守護霊も全部別財布にする必要がある**」「**開発後は特に指標がないなら全て独立させて、
  ちゃんとしたい。**」(2026-08-23・GHOST_PARITY_LEDGER.md ★裁定に記録済み)
- 「**敵なんだから共有するわけが無い。普通にAIとの対戦として考えれば分かること**」(2026-08-23)
  = 幻影の設置物・召喚・回復は**1対1の対戦としてそのまま鏡**にする。帰属に迷う余地は無い。

## 「ではない」条件(労力をかけない所)
- **リアルタイム対人戦ではない。** 戦うのは「記録されたビルド+癖」であって、生身の相手ではない。
  同期・遅延補償・マッチメイキングの類は対象外。
- **数値の精密バランスは対象外**(叩き台を出し、実機で社長が調整する)。
- **専用素材・UIの磨きは対象外**(既存の絵と枠を流用)。
- **サーバの新規開発は対象外**(既存の `src/online/` を流用する。増設が要ると分かった時点で別案件)。

## 2. 設計の背骨 — 「写すな、共通化しろ」を主語の統一で実現する

これまでの漏れ(守護霊にスキル倍率が乗らない・幻影が銃の基礎値しか使わない)は、すべて
**「プレイヤー用に書かれた計算を、他の主語ぶんもう一度書こうとして書き漏らした」**ことに由来する。
写経を続ける限り、**プレイヤーに何か足すたびに3箇所へ手で写す**必要があり、必ずどこかが漏れる。

**背骨**: `combatActorPlayer(actorId)` を**3者対応に一般化**し、戦闘系の関数はすべて
**主語を引数で受ける**(既定=プレイヤー)。これが済むと以後
**「プレイヤーに足した機能は、何もしなくても3者に乗る」**。

- **読み**: 疑似Playerを1枚組んで返す(ビルド+実体の座標/寸法/HP+その主語の状態)。
- **書き**: 宛先を主語で振り分ける専用の setter を通す。
- **幻影は Enemy シャーシ、守護霊は Summon シャーシ**のままでよい。
  「storeに2人目のプレイヤー実体を立てる」(GHOST_BOSS.md の北極星・**コスト8/10**)は**やらない**。
  疑似Playerで同じ効果が得られており、既に守護霊で実証されている。

## 3-b. O-1 の詳細(発注できる粒度・2026-08-23 実コードで確認)

### なぜ安いのか
**`ghostActorPlayer(build, actor)`(`utils/ghostBuild.ts:79`)の第2引数は構造型**
`{x, y, width, height, health, maxHealth}` **であって Summon 型ではない**。
`Enemy` はこの形をそのまま満たすので、**幻影を渡すだけで通る=新しい式を1本も書かない**。
`resolveGhostBuild(snap, live)` も純関数なので同じく流用できる。

### ★O-1 で必ず直す実バグ予備軍(走査で発見)
`ghostBuildFor`(`utils/ghostBuild.ts:64`)のメモ化は **`cached = { id, build }` の1件だけ**。
現状は守護霊が同時1体なので露見していないが、**守護霊と幻影が同時に居ると id が交互に変わり、
毎フレーム `resolveGhostBuild`(武器生成を含む)を作り直す**。
コメント自身が「ここで実体側の帳簿を重ねないとCD表が召喚時点で凍る(v0.25.2525の実バグと同型)」と
警告している系統そのもの。**O-1でキャッシュを id をキーにした Map へ広げる**(上限は同時実在数=数件)。

### 作業(A〜E)
| | 中身 | 触る場所 |
|---|---|---|

### 受け入れ条件
1. `combatActorPlayer(<幻影のid>)` が、**幻影の座標・寸法・HP** と **`phantomBuild` 由来のスキル/装備/クリ率/サブウェポン**を載せた1枚の `Player` を返す。
2. 幻影の `subWeaponCooldowns` が **プレイヤーとも守護霊とも独立**している(3者が別財布)。
3. **プレイヤー単体の挙動が1bitも変わらない**(`actorId === undefined` の経路は従来のまま)。
4. 幻影が居ない / `phantomBuild` が無い時は **`null` を返し**、呼び出し側が従来経路へ落ちる。
5. **守護霊と幻影が同時に居ても `resolveGhostBuild` が毎フレーム走らない**(キャッシュのテストを同コミットで書く)。
6. この段では**まだ何も強くならない**(配管だけ。強さが乗るのは O-2)。

当初「中」としたが、`ghostActorPlayer` が構造型で Enemy をそのまま受けるため **「中の下」**。
新規の計算式はゼロで、作業の実体は**型2つ・分岐2箇所・スポーン1行・キャッシュ1箇所**。

### O-1 に含めない(=別の場所で決める)

## 4. デメリット — **開発だけではない。開発以外が4つある**

### D1. ゲーム全体の再バランスが必ず必要になる(最大・開発ではない)
3者がフルビルドで同じ土俵に立つと、**幻影は「世界の誰かの最強ビルド」**になりうる。
一方プレイヤーは**雑魚も捌きながら**戦う。**同条件は"公平"ではない。**
段2(ステータス)の直後に必ず表面化する。**これは実装で解決できず、社長の調整でしか収束しない。**

### D2. 「合法だが強すぎる」ビルドは素通りする(不正の残余)
`shared/ghostSanitize.mjs` は**ホワイトリスト+クランプまでは既にやっている**
(damageMult 0.1〜5 / critChance 0〜1 / skills ≤24・Lv≤3 / subWeapons ≤4 / 64KB上限)ので、
**でたらめな値の注入は既に防げている**。残るのは「**全項目が合法な上限**」のビルドで、
これは改造しなくても**やり込んだプレイヤーなら普通に到達する**。
⇒ 「倒せない幻影が配られる」可能性。**上限そのものの設計(強さの天井)が要る**=D1と同根。

### D3. 運用が続く(開発ではない・恒久)
「世界中のデータ」は**サーバが動き続ける**ことを意味する。配布方針は
「**Web公開はしない。最終形=アプリ配布(ストア)**」(v0.25.2549)なので、
**本体は売り切りでもサーバ代だけは毎月続く**。
加えて、他人の**名前・コメント**が流れる仕組みが既にある(`ghostComment` / `playerName`)以上、
**通報・遮断の責任**も持つことになる。※既存 `src/online/` の運用実態(どこで動いているか・費用)は
**本計画では未確認**。段5の着手前に確認が要る。

### D4. 将来の全機能への恒久税(開発だが、1回では終わらない)
主語を引数化すると、**以後プレイヤーに何か足すたびに「3者ぶん正しいか」を考える必要**が出る。
ただし段1をちゃんとやれば**「自動で乗る」側に倒せる**ので、実際の選択は
**「税を払う」か「毎回3箇所へ手で写して漏らし続ける」か**であり、前者が明確に安い。

### D5. 実行時コスト(**軽微・対策込み**)
- **唯一の有料項目=同時に出ている強glow**(`kind:'glow'` かつ `radius >= STRONG_GLOW_RADIUS`=44px)**の数**。
  実測 **1個 ≈ 2ms/フレーム(予算の約12%)**。爆発系サブを3者が同時に撃つと瞬間的に増える
  (寿命240〜900msなので持続はしない)。⇒ **段3で同時上限を持たせる**(明記済み)。
- 常駐召喚(錬金/タレット)が最大3セット。実測では敵36体(重量級)+弾70+粒子64 で 60fps 張り付きなので
  **効かないはず**だが、段3の実機で確認する。
- CD帳簿の別財布化そのものは**データ数百バイト・per-frame増分ゼロ**(判定の回数は変わらず、読む場所が変わるだけ)。
