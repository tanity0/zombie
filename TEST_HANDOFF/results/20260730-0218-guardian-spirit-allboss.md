## 1. 検証した仕様(コードから確定)
`guardian-spirit` は**最初から全員所持**の超レア(`DEFAULT_OWNED_SKILLS`)。発動は
`ghostRunEnabled()` = **`?ghost=1`(開発用) OR 守護霊を装備**(`ghostDriver.ts:113`)。
ボス交戦の**立ち上がりの瞬間**(`BOSS_ENGAGE_ENTER_PX=900` 以内・`dormant`でない)に:
1. `ghost-ally` を**1体**召喚(同時1体)
2. ボスの `health`/`maxHealth` を **×1.6**(`GHOST_BOSS_HP_MULT`)、`ghostHpBoosted` で**二重適用防止**
3. `ghostSummonedThisRun = true`(リザルトのスコア×0.5がこれを見る)
4. 紐付いたボス(`ghostBossId`)が `enemies` から消えたら**解散**

対象ボスは `ENGAGEABLE_BOSS_TYPES`(`bossEngagement.ts:24`)に**全13体が登録済み**。

## 3. 途中で「バグらしく見えた」2件 — どちらもテスト側の不備(製品バグではない)
### 3-1. 「ボスHPが×1のまま」= 計測タイミングの問題
11ケースで `HP N→N(×1)` と出た。原因は**観測が遅かっただけ**。
裏ボス/ゲート2ボスは force-spawn で**プレイヤーの至近に湧く**ため、**湧いた瞬間に交戦成立してブーストが入り**、
1秒後の初回ポーリング時には既に適用済みだった。**素HP×1.6と観測値が全ケースで完全一致**するのが証拠:
```
mimir 6666×1.6=10665.6→10666 ✓ / jormungand 7500×1.6=12000 ✓ / skadi 10000×1.6=16000 ✓
thor 11000×1.6=17600 ✓ / ゲート2勢 2000×1.6=3200 ✓ / idol 9000×1.6=14400 ✓
```
城ボス(#1/#13)だけ「2500→4000」の遷移を捉えられたのは、**城で `dormant` 待機していて
プレイヤーがワープするまで交戦が始まらなかった**ため。=機構の裏付けにもなっている。

### 3-2. 「idolだけ解散しない」= ①別個体を消していた ②シミュがポーズ中だった
- **①**: `?idolnow=1` を使うと **idolが2体存在**する(原点から約-7300pxに配置された `dormant` の本来の個体 +
  force-spawnされたプレイヤー近傍の個体)。最初の追試で私は**守護霊が紐付いていない方**を削除していた
  (`同一id生存=false` なのに `idol数=1` のまま=別個体が生存)。
- **②**: 紐付き個体を正しく削除しても解散しなかったが、計測を足したところ
  **`isPaused=true`・`gameTime` が 17ms で凍結**していた。**stage-2 は序盤でポーズが入る**(チュートリアル等)。
  ゲームループ全体が `!isPaused` ゲートの内側(`useGameLoop.ts:1837`)なので、**解散判定も含めて何も動いていなかった**。
- **③ 最終確認**: ポーズを解除して再試行 → `gameTime` が 33ms→767ms と進んだ**その瞬間に解散**(`ghost数=0`)。
  → **idol の解散も正常。**

## 4. v0.25.2468 の主機能「スナップショット100%再現」の検証(別途実施)
**13ケース全てで守護霊が `HP110/110・Lv1・warrior・speed87` 固定**だった。これは**フォールバック**であり、
`loadPlayerProfile()` が null(=計測プロファイル未記録)だったため。
理由は仕様どおり: **守護霊ラン/`?ghost=1` ランは計測を丸ごと停止する**(§2.7 制約1)。
→ つまり**主機能そのものが13ケースでは一度も通っていない**ので、プロファイルを仕込んで別途検証した。

`localStorage['zombie-ghost-profile-v1']` に本人値と紛れない値を仕込んだ結果:
| | maxHP | speed | Lv | class |
|---|---:|---:|---:|---|
| 仕込んだ snapshot / srcClass | **777** | **123** | **9** | **rogue** |
| 本人(プレイヤー) | 110 | 87 | 1 | warrior |
| **実際に出た守護霊** | **777** | **123** | **9** | **rogue** |

**→ スナップショット100%再現 = OK**(本人値ではなく計測時の値がそのまま出ている。
`srcClass` による絵の切り替えも効いている)。

## 5. 気づき(判定は設計チャット)
1. **`?idolnow=1` は idol を2体にする**(配置済みの `dormant` 個体を消さずに追加する)。
   デバッグ導線の副作用なので実プレイには影響しないが、**idolのテスト時に「どちらの個体か」を
   意識しないと誤判定する**(私が実際に踏んだ)。将来 idol を自動テストするなら申し送り事項。
2. **stage-2 は開始直後にポーズが入る**(チュートリアル等)。**stage-2 を自動テストする時は
   ポーズ解除が必要**(そうでないとシミュが1フレームも進まず、何を検証しても「動かない」と見える)。
3. 守護霊のHPは**フォールバック時は本人の maxHealth と同値**(×0.6の減額=旧 `GHOST_HP_FRAC` は廃止済み)。
   初回プレイ(プロファイル未記録)では**守護霊が本人と同じHP**になる、という理解で合っているかは設計判断。

- 検証したのは**召喚/HP倍率/フラグ/同時数/紐付け/解散/ステータス再現**の**配線**。
  **守護霊の戦闘挙動**(実際にボスを攻撃するか、サブウェポンを使うか、リーシュで瞬間ワープするか等)は
  headedのスロットリングで実戦が進まないため**未検証**。そこは実機で社長が確認する項目。
- ボスの「死亡」は `enemies` から削除して模した(実際に6000〜17600HPを削るのは時間がかかるため)。
  解散条件①の判定コードは `ghostBossId` の生存だけを見るので、実際の撃破と等価。
