## 何が変わったか(コード確認・`src/utils/cameraZoom.ts`)
v0.25.2412 で**ボス戦専用の引き `BOSS_ZOOM_MIN`(既定 0.7)が新設**された(社長指示「ボス戦はもう少し引けますか」)。
通常戦闘の引き(体数ドリブン)は据え置き。

| | 変更前 | 変更後 |
|---|---|---|
| 通常戦闘の最大引き `CONTEXT_ZOOM_MIN` | 0.8 | **0.8(据え置き)** |
| ボス戦の引き `BOSS_ZOOM_MIN` | — | **0.7(新設・`?bosszoom=` で0.3〜1に調整可)** |
| 絶対最深 `ZOOM_MIN_ABS` | 0.8 | **0.7** |
| 最深時の可視域 | 画面の1.25倍 | **画面の1.43倍** |

- `contextZoomTarget()` は **大型敵が1体でもいれば体数に関係なく即 `BOSS_ZOOM_MIN`**。
  対象(`LARGE_ZOOM_TYPES`)= `reaper / giantbat / mimir / jormungand / skadi / thor / hunter` の7種。
- コード自身が「**安全マージンの基準は `CONTEXT_ZOOM_MIN` ではなく必ず `ZOOM_MIN_ABS` を見ること**、
  ズレると v0.25.1324/1325 の潜伏バグが再発する」と明記している。

### ★テスト条件の注意(前回と同じやり方では検証にならない)
**`?zoomlock=1` は `CONTEXT_ZOOM_MIN`(0.8)に固定するだけで、新しい最深0.7を踏まない**
(`cameraZoom.ts:44` `if (v === '1') return CONTEXT_ZOOM_MIN`)。
→ 今回は**数値指定**で明示的に 0.7 / 0.65 を踏んだ。前回(v0.25.2404)の `zoomlock=1` のままでは
**変更部分を一度も通らない**ので、次回以降も同じ注意が要る。

## 手法メモ(限界)
- headedの複数ウィンドウ撮影では Chrome の背景rAFスロットリングでシミュが進まず、各ショットは
  **gameTime 1秒前後・敵0体の序盤フレーム**(既知の制約)。
  そのため**「実際にボスが出て自動で0.7へ引かれる瞬間」は撮っていない**。
  代わりに **`?zoomlock=0.7` で同じズーム値を強制**して描画を検証している(ズーム値そのものは同一なので、
  レイアウト/カリング/オーバースキャンの検証としては等価)。
  **ボス出現時の"引きの動き"(補間の滑らかさ・切り替わりの見え方)は実機で社長が確認する項目。**
- 横持ちは対象外(社長指示「横はいらない」)。
