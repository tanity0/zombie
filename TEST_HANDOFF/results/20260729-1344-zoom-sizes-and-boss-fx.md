# ① ズーム引き値変更後の各サイズ描画崩れ

## 変更内容(コード確認)
`src/utils/cameraZoom.ts:10` **`CONTEXT_ZOOM_MIN = 0.8`**(コメント: 「社長指示で引き幅2倍: 1.0→0.9 の 0.1 → 0.2」)。
= **最大引き時の可視域が画面の1.11倍 → 1.25倍**へ拡大。CLAUDE.md「ズーム引き考慮(必須)」に従い
**`?zoomlock=1`(常時最大引き)を必ず含めて**確認した。

## 結果: **描画崩れは検出されず(5サイズ × 通常/最大引き = 10条件すべて)**
| サイズ | 端末目安 | 論理bounds | 通常 | **最大引き(zoomlock)** |
|---|---|---|---|---|
| 360×800 | 小Android | 405×900 | 崩れなし | **崩れなし** |
| 375×667 | iPhone SE/最も横広 | 405×720.2 | 崩れなし | **崩れなし** |
| 390×844 | iPhone 13-15標準 | 405×875.6 | 崩れなし | **崩れなし** |
| 412×915 | Pixel | 405×899.7 | 崩れなし | **崩れなし** |
| 430×932 | iPhone Pro Max/最も縦長 | 405×877.0 | 崩れなし | **崩れなし** |

- **論理幅は全サイズ405に正規化**され、高さがアスペクト比で伸びる方式。引きが広がっても
  **背景・霧・木・NPC・敵・HUDのいずれにも欠け/隙間/二重描画/レターボックスは出ていない**。
- 最大引きでは意図どおり自機が小さくなり可視域が広がる(通常との差も確認済み)。

## HUDはみ出しの機械判定(目視に頼らない確認)
スクショ上で**右のサブウェポンパネルが画面端ぎりぎり**に見えたため、目視で断定せず
**DOMの実座標(`getBoundingClientRect`)がビューポートを超えるか**を全条件で機械的に測った。
```
全10条件: 横あふれ=false / はみ出し要素=0 → 問題のあった条件 0/10
```
→ **パネルは「際どいが範囲内」。はみ出しではない。**(生データ `_zoom-hud-overflow.json`)

# ② ボス系エフェクト: どこまで何が入っているか

## 結論: **新エフェクト7素材は、すべて `giantbat` 型にのみ適用**(13体中2系統)
描画呼び出しが `if (e.type === 'giantbat' && GIANT_SCRIPT_ENABLED)` ブロックの**内側にしか存在しない**
(`pixiScene.ts`。`drawTelegraphRing`=9091/9136、`drawTelegraphBand`=9014/9111、`drawSlashArc`=9119、
`drawDust`=9078、遅延起爆ループ=9266 も同ブロック内)。

| 素材 | 中身 | 適用先(技) |
|---|---|---|
| **A-1** `fx/telegraph-ring` | 予告円の輪 | 踏み鳴らし(`g-stomp-windup`)/ 飛び掛かりの着地予告(`g-jump-windup`/`air`) |
| **A-2** `fx/telegraph-band` | 予告帯の縁 | 薙ぎ払い(`g-sweep`)+ 共通ヘルパ `drawGiantCapsuleZone` 経由で**噛みつき/のしかかり/滑空/翼撃/掃射/伸びる触手** |
| **D-1** `fx/slash-arc` | 斬撃の弧 | 薙ぎ払いの **active の瞬間だけ**(`g-sweep-active`) |
| **B-0** `fx/dust` | 砂埃 | **硬直の最初420ms**(踏み鳴らし/着地/のしかかりの recover)。`dustTintForStage()` でステージ別に着色 |
| **D-2** `fx/claw-mark` | 爪痕 | 遅延起爆キューの**帯タイプ(氷を除く)**= 滑空の二撃目・翼撃の三拍目 等 |
| **E-5** `fx/blood-pool` | 血溜まり | 遅延起爆キューのうち **`floorUntil` 付き = グレンの「血の弧」だけ** |
| **C-1** `fx/muzzle-flash` | 銃口フラッシュ | **ボスではなくプレイヤーの発砲**(`pixiScene.ts:7803`) |

### エフェクトが乗るボス(giantbat 型)
- **城ボス=ジャイアント(ステージ1〜6)**
- **グレン(stage-7)** … `spawnEnemyAt('giantbat', …)` + `isStoryBoss` + `storyBossVariant='stage-7'`(`useGameLoop.ts:2313-2319`)
- **EX(未確認変異体)** … 同経路の `storyBossVariant='stage-ex1'`

### エフェクトが乗っていないボス(11体)
- **ゲート2ボス6体**: ミゲル / ジブリル / ラフィ / ウリ / スリィエル / アクラシエル
- **裏ボス4体**: ミーミル / ヨルムンガンド / スカジ / トール
- **idol**(stage-2 隠しボス)
→ これらは従来どおり **Graphics のベタ描き**(`drawMiguelKatanaReady` / `drawMiguelSlash` 等の専用関数、
  または `o.poly().fill()` / `o.ellipse().stroke()`)で予告を出している。**A-1/A-2 を呼ぶ箇所は giantbat ブロック内の4箇所のみ。**

**「ボス系全てに入れた」という認識に対し、実際は 13体中 giantbat系のみ。11体は素材化されていない。**
段階適用(まず城ボスから)の途中なのか、漏れなのかは**設計チャットの判断**。

### 付随: コメントと実態のズレ(軽微)
`drawClawMark` 付近のコメントに「氷(**スカジ**/城ボスstage-4)は爪ではないので付けない」とあるが、
**スカジ本体はこの描画ループに到達しない**(giantbat ブロック内のため)。コメントが実態より広く読める。

# ③ 新規バグ: changelog のバージョン重複で React エラー(全サイズ・全条件で発生)

## 事象
**全10条件で各2件・計20件**の console エラー:
```
Warning: Encountered two children with the same key, `%s`. … 0.25.2364
    at div
```

## 原因(特定済み)
`src/data/changelog.ts` の **281行目と287行目で `version: '0.25.2364'` が重複**している。
更新情報のリストがバージョンを React の `key` に使っているため、キー衝突になる。
```
281:  { version: '0.25.2364', items: ['ゲーム内容の変更はありません(開発用プレイヤーAIの調整のみ…)'] },
287:  { version: '0.25.2364', items: ['ゲーム内容の変更はありません(残りのボスを…設計文書のみ)'] },
```
**内容が別物**なので、**どちらかのバージョン番号が間違っている**(採番ミス)と思われる。

## 影響
- Reactの警告レベルはerror。**「重複/欠落が起きうる」挙動**なので、更新情報の項目が
  表示されない/重複するリスクがある(実害の有無は未確認)。
- **ズーム変更とは無関係**。前回(v0.25.2332)の同種テストではエラー0件だったので、**この34版で入った新規**。
- 直すのは1行(片方のバージョン番号を正しい値へ)。**判断・修正は設計/実装チャット**。

## 手法メモ(限界)
- headedの複数ウィンドウ撮影では Chrome の背景rAFスロットリングでシミュが遅く、
  各ショットは **gameTime 1〜3秒・敵0〜1体の序盤フレーム**(既知の制約・前回報告済み)。
  **レイアウト/ズーム/HUDの崩れ判定には十分**だが、**敵が多数出た時のズーム挙動(文脈ズームが最大まで引く状況)は
  この方法では再現できない**。そこは `?zoomlock=1` で代替した(最大引きを強制)。
- **ボスのエフェクトは実際に描画させて目視確認していない**(②はコード上の適用範囲の走査)。
  実際の見え方(砂埃の量・色・長さ等)は `REALDEVICE_TEST.md` のとおり**実機で社長が確認**する項目。
